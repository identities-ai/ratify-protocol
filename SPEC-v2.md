# Ratify Protocol Specification v2

**Status:** Draft for implementation and independent review. This document is not published or a production security claim.
**Wire version:** 2. **Signing suite:** fixed hybrid Ed25519 and ML-DSA-65 (FIPS 204).
**Relationship to v1:** v2 is a breaking, separately versioned protocol. Implementations MUST select exactly one version at an API boundary. A v2 verifier MUST reject v1 objects and MUST NOT fall back. A v1 verifier continues to implement the immutable v1 contract in `SPEC.md`.

## 1. Scope and compatibility

This specification defines the v2 wire profile and verifier rules. v2 deliberately does not preserve v1 signature bytes, key identifiers, challenge rules, or acceptance behavior. Issuers generate fresh v2-only keys. Importing a v1 key into a v2 identity is prohibited. v1-to-v2 migration is a clean re-enrollment: establish the person or organization identity out of band, generate new v2 keys, enroll proof of possession, and issue new v2 delegations. There is no cryptographic continuity claim from a v1 key and no v1 key may authorize a v2 key. Preserve the old v1 release and its artifacts for users who pin it.

The Verify product may publish a migration schedule for its hosted APIs. That schedule does not alter the offline v1 specification or require every third-party verifier to accept v2.

## 2. Terms and encoding

MUST, MUST NOT, SHOULD, and MAY are normative. JSON objects use the v1 `RatifyCanonicalJSON` profile in SPEC.md §§6.1–6.3, including ascending UTF-8 byte-order keys, U+2028/U+2029 escaping, safe integers only in the range ±(2^53−1), valid Unicode scalar strings without normalization, and no duplicate keys, unless a field below is explicitly encoded as fixed-width bytes. The value model is restricted as specified in SPEC.md §5.7.1. Parsers reject duplicate keys, unknown fields in signed v2 structures, non-canonical encodings where the SDK exposes canonical wire bytes, and malformed base64. All JSON integers are safe integers; timestamps are Unix seconds. Byte strings use canonical padded RFC 4648 base64. Hex identifiers are lowercase.

The v1 hybrid public-key and signature component sizes and encodings are retained: Ed25519 public key 32 bytes and signature 64 bytes; ML-DSA-65 public key 1952 bytes and signature 3309 bytes. v2 fixes these algorithms and sizes. No object or caller negotiates an algorithm or context. ML-DSA implementations MUST implement final FIPS 204, not the 2023 draft. Ed25519 uses canonical compressed Edwards encodings: decode A and R, reject y ≥ 2^255−19, reject S ≥ L, and require both A and R to be non-identity points in the prime-order subgroup (`[L]P = identity`). Verify the cofactorless RFC 8032 equation `[S]B = R + [k]A`, where `k = SHA-512(R_encoding || A_encoding || M) mod L`. ZIP-215 acceptance, non-canonical encodings, small-order or mixed-order points are rejected. SDKs MUST match these checks exactly.

Wire decoding is semantic: a v2 decoder parses the strict JSON, validates every field, and verifies signatures over the RatifyCanonicalJSON re-encoding of the decoded value, so equivalent literal and escaped spellings of the same string (for example a literal or escaped U+2028) are the same signed value. Two spellings are nevertheless rejected as `malformed` before parsing because a lenient parser would map them onto a different valid value: an unpaired UTF-16 surrogate escape (`\uD800`–`\uDFFF` not forming a high-low pair), and the number spelling `-0`. Released v1 decoders are unchanged.

### 2.1 Identity identifiers

`key_id_v2 = lowercase_hex(SHA-256(ASCII("ratify-key-id-v2") || 0x00 || ed25519_public_key || ml_dsa_65_public_key))`.
The component order and byte encodings are fixed: the Ed25519 public key is exactly 32 raw bytes and the ML-DSA-65 public key is exactly 1952 raw bytes. The output is the full 32-byte digest encoded as 64 lowercase hexadecimal characters. The version label prevents v1/v2 identifier aliasing. A v2 verifier recomputes every ID from the complete key and rejects mismatch before status lookups. IDs are lookup indexes, not substitutes for key material: after lookup, the full public key MUST match; zero or multiple matching records fail closed. Signed objects that use a key ID MUST also bind the complete key or authenticated key material.

### 2.2 Operation and session context

`lp(x)` is `uint64_be(byte_length(x)) || x`. Text is UTF-8 without Unicode normalization; malformed Unicode is rejected. The operation preimage is
`ASCII("ratify/operation-context/v2") || lp(required_scope) || lp(operation) || lp(resource_id) || lp(requested_path) || lp(payload_digest)`.
`payload_digest` is empty or exactly 32 bytes. `request_hash = SHA-256(operation_context_bytes)`.
`required_scope` MUST be non-empty and exactly one canonical, registered scope from `SPEC.md` §9. A wildcard or `custom:` extension is not a valid required action scope. The same rule applies to each transaction party's `required_scope` below. A verifier MUST reject an invalid required scope before constructing or checking the corresponding context.
The session preimage is
`ASCII("ratify/session-context/v2") || lp(verifier_id) || lp(workspace_id) || lp(agent_id) || lp(session_id) || lp(invocation_id) || lp(request_hash)`.
`session_context = SHA-256(session_context_bytes)`, exactly 32 bytes. An absent operation input is encoded as an empty `lp` field. `session_context` in a proof bundle is null or exactly these 32 bytes. Verifiers that require action/session binding MUST recompute it from authenticated request state and reject a mismatch. An unbound generic verification MUST report that no session/action context was evaluated. For this formula, `verifier_id` and `agent_id` are canonical lowercase 64-character hexadecimal v2 key IDs encoded as UTF-8 text; `workspace_id` is its canonical lowercase UUID text encoded as UTF-8; `session_id` and `invocation_id` are UTF-8 text without Unicode normalization; `request_hash` is the exact 32 raw SHA-256 bytes, not its hexadecimal or base64 text.

The Verify API represents an optional payload digest as JSON `null` or canonical text `sha256:` followed by 64 lowercase hexadecimal characters. The Go interoperability helper `DecodePayloadDigest` maps `nil` to an absent digest and rejects an empty string, uppercase text, wrong length, or non-hexadecimal input. This HTTP representation is not a Protocol proof encoding; Protocol SDKs that do not implement the Verify API need only accept the raw empty or 32-byte digest described above. The shared API decoder vectors are in `testvectors/v2/operation-session-context.json`.

When a verifier requires session binding, its authenticated request state MUST supply the expected Protocol v2 `verifier_id`. That value MUST equal both the proof bundle's `verifier_id` and the authenticated `ExpectedChallenge.verifier_id`; the verifier rejects any mismatch before challenge claim. The value comes from caller-authenticated verifier-key configuration and cannot be selected by the API caller.

Transaction context is `SHA-256(ASCII("ratify/transaction-context/v2") || lp(transaction_id) || lp(terms_schema_uri) || SHA-384(terms_canonical_json))`. For each party, `transaction_party_request_hash = SHA-256(ASCII("ratify/transaction-party-request/v2") || lp(transaction_context) || lp(required_scope))`. This per-party value is the `request_hash` input to that party's session-context construction. Each party record carries `verifier_id`, `workspace_id`, `agent_id`, `session_id`, `invocation_id`, and `required_scope`, allowing any verifier to recompute the complete context and the exact scope claim.

## 3. Typed signing contract

Each signed statement has a permanent `object_type_code` from the registry in §4. The exact signable projection is explicitly named for each schema in §5. Each schema specifies whether an optional field is omitted or encoded as JSON null. Unknown fields are rejected before projection; implementations MUST NOT silently strip them. All fields included by that schema's projection, including version, signer role, identifiers and key material, are covered. The signer key is either carried in the signed body or resolved through authenticated caller-supplied configuration. A signature envelope never chooses or overrides a key.

Compute `d = SHA-384(signable_bytes)`. The exact message signed by both components is the following 77-byte string:

```
M = ASCII("ratify-protocol-signature") || 0x00 || 0x02 ||
    uint16_be(object_type_code) || d
```

Both Ed25519 and standard pure ML-DSA-65 sign the identical `M`. ML-DSA uses the FIPS 204 context `ASCII("ratify-protocol/2/") || lowercase_hex_4(object_type_code)` (22 ASCII bytes, for example `ratify-protocol/2/0001`). The context is selected by the verifier from this registry, is never supplied by the message, and is not negotiated. Empty, unknown, or mismatched contexts fail verification. The Ed25519 prefix provides message-level domain separation; it is not Ed25519ctx.

This profile hashes the canonical object to define a short Protocol message and then applies pure ML-DSA-65 to that message. It does not invoke the FIPS 204 HashML-DSA mode, Ed25519ph, or Ed25519ctx. The SDK computes `M` and the context. A direct-message provider receives those exact bytes. Where the provider exposes only external-μ signing, the SDK computes FIPS 204 `tr = SHAKE256(pk, 64)` using the 1952-byte ML-DSA public key bound to the identity and `mu = SHAKE256(tr || 0x00 || uint8(context_length) || context || M, 64)`, then passes only `mu` to the external-μ operation. Such a KMS key is a generic 64-byte signing oracle; it cannot enforce type code, context, or protocol version. The trusted SDK/signer adapter MUST enforce those rules before calling it, protect key-use authorization, and verify every returned signature using the ordinary FIPS 204 verifier. Conformance compares exact `M` and `mu` bytes and verification results; signature bytes may differ when a provider uses permitted hedged signing. Test fixtures use fixed deterministic randomness. The adapter MUST NOT expose arbitrary caller-selected messages, prehash modes, or contexts. Both signatures are mandatory; partial, swapped, stripped, or cross-version signatures fail. SHA-384 collision resistance is part of this profile's security assumption. SHA-384 is part of the v2 wire contract and MUST NOT be substituted.

## 4. Signed object registry

Codes are permanent and never reused. A v2 verifier rejects unknown codes. The code is in the signing transcript, and its meaning is also fixed by the schema being verified.

| Code | Object | Signer role |
|---|---|---|
| `0x0000` | Reserved; invalid | None |
| `0x0001` | Delegation certificate | Declared issuer key |
| `0x0002` | Challenge presentation | Presenting agent key |
| `0x0003` | Revocation list | Authenticated issuer status key |
| `0x0004` | Key-rotation statement authorization | Current old key |
| `0x0005` | Revocation push | Authenticated issuer status key |
| `0x0006` | Witness entry | Named witness key |
| `0x0007` | Transaction receipt party statement | Each named party key |
| `0x0008` | Verification receipt | Caller-authenticated verifier key |
| `0x0009` | Key-rotation statement proof of possession | New key |

The signing API takes an explicit typed object and returns its signature; it does not accept an arbitrary numeric code. The verifier derives the code from the concrete schema. A v2 registry extension requires a specification revision and conformance vectors before implementation.

`ChallengeClaimDigest(c) = SHA-384(ASCII("ratify-protocol-challenge-claim-v2") || 0x00 || c)` for the 32 decoded challenge bytes. Replay stores key claims by `(locally_configured_verifier_namespace, replay_epoch, ChallengeClaimDigest)`; in managed Verify, `replay_epoch` equals `verify_replay_epoch` and atomically retains them until time is strictly later than `expires_at + configured_clock_skew`. Challenge validity uses an exclusive expiry boundary: `now < expires_at`; skew bounds future `issued_at` values only and never extends validity after expiry.

`StatementBodyDigest(code, body) = SHA-384(ASCII("ratify-protocol-statement-body-v2") || 0x00 || uint16_be(code) || RatifyCanonicalJSON(body))` compares a signed intent independent of randomized signature bytes. Rotation, witness, and verification-receipt chains use this digest as their predecessor hash so randomized signature bytes cannot create false forks.

`StatusEvidenceDigest(code, object) = SHA-384(ASCII("ratify-protocol-status-evidence-v2") || 0x00 || uint16_be(code) || RatifyCanonicalJSON(object))` hashes the complete canonical signed revocation object, including its signature. It is a reference to exact status evidence, not proof that a verifier independently evaluated freshness or policy.

`BundleHashV2(b) = SHA-384(ASCII("ratify-protocol-bundle-v2") || 0x00 || RatifyCanonicalJSON(b))`, including all certificate and challenge signatures. Verification receipts and transaction receipt party bindings use this exact function.

## 5. Wire schemas

v2 uses the v1 object semantics only where this section explicitly says so. Every v2 object has `version: 2`. Identifiers are recomputed from complete keys. Every field listed as required is present, including empty arrays. Unknown fields are rejected. Public keys and signatures retain the v1 JSON shape.

### 5.1 Delegation certificate

Required fields: `version`, `cert_id`, `issuer_id`, `issuer_pub_key`, `subject_id`, `subject_pub_key`, `scope`, `constraints`, `issued_at`, `expires_at`, `signature`. `version` is exactly 2. `cert_id` is a non-empty UTF-8 opaque identifier, unique within `(issuer_id, cert_id)`. `scope` is a bounded array of strings. The array shape, string types, and resource bounds are checked before challenge claim; non-emptiness, registry membership, uniqueness, wildcard rules, and the `custom:*` prohibition are post-claim authorization checks that return `invalid_scope`. A v2 issuer MUST emit a non-empty unique list of valid scopes. `constraints` uses the v1 constraint object shape and closed-world rule, plus the v2 built-in `ratify.receiver_audience` defined below. Unknown types fail closed. `issuer_id` and `subject_id` MUST match the v2-derived IDs of their complete keys. The signable projection is every field except `signature`. The issuer signs code `0x0001`.

The `ratify.receiver_audience` constraint has exactly `type` and `params`. `params` has `exact_receiver_ids` and `trust_domain_ids` arrays, with at least one array non-empty; values are unique, non-empty, canonical opaque IDs, compared by exact UTF-8 byte equality. If `trust_domain_ids` is non-empty, `max_membership_age_seconds` is required and is a positive safe integer; otherwise it MUST be absent. No other fields are allowed. A receiver ID is the stable receiver identifier in the authenticated expected challenge, not `verifier_id` (the verifier key ID). Constraint structure, canonical encoding, and signatures are checked before challenge claim. An expected challenge MUST include the independently configured `expected_receiver_id` whenever any chain certificate contains this constraint; absence is a pre-claim failure. Per certificate, the receiver is eligible when it matches an `exact_receiver_ids` entry OR when one named domain has valid membership evidence. A certificate with only exact IDs that exclude the receiver is rejected by the pure local hook before claim. If domains are also present, a non-matching exact ID alone is not a failure; domain membership is resolved after claim from authenticated local trust configuration or an authenticated provider. The proof cannot select its source or URL. Missing, stale, or unverifiable membership yields `constraint_unverifiable`. A valid nonmatch yields `constraint_denied` only when caller-authenticated, authoritative membership evidence for that constrained link completely rules out every named domain. A statement proving membership in an unrelated domain alone does not prove nonmembership in a named domain and is `constraint_unverifiable` unless the source establishes that the domain set is complete. Across the chain, every certificate carrying an audience constraint must independently match, so the chain result is the intersection of per-certificate eligibility; absence at a link imposes no narrowing. When several links name domain audiences, enforce the smallest `max_membership_age_seconds` among all domain-constrained links. An empty effective intersection yields `constraint_denied`. If multiple domain-constrained links produce mixed outcomes, any valid mismatch yields `constraint_denied`; only when no link mismatches does any missing or unverifiable required membership yield `constraint_unverifiable`. Protocol does not impose a risk floor; a relying application's high-risk policy may require a present audience and records its own policy outcome separately from the Protocol receipt.

As in v1, every non-root issuer in a delegation chain MUST have received the sensitive `identity:delegate` scope in its parent certificate. A chain hop whose parent certificate omits that exact scope is denied with reason `delegation_not_authorized` and identity status `delegation_not_authorized`; scope intersection alone does not authorize an agent to issue further delegations. The `not_delegated` reason is reserved for an empty chain.

The shared v2 vectors MUST cover two domain-constrained links where one returns a valid non-match and the other has missing or unverifiable membership; the terminal result is `constraint_denied` regardless of link evaluation order.

When one proof contains multiple independently evaluated deterministic constraints, aggregate completed results without depending on chain traversal order: any proven violation yields `constraint_denied`; otherwise any unknown constraint yields `constraint_unknown`; otherwise any unavailable or unverifiable constraint yields `constraint_unverifiable`. Exact-only receiver-audience mismatch remains the specified pure pre-claim rejection with no Protocol receipt. Vectors MUST cover mixed audience and non-audience constraint outcomes in both link orders.

### 5.2 Proof bundle and challenge presentation

Required bundle fields: `version`, `verifier_id`, `agent_id`, `agent_pub_key`, `delegations`, `delegation_digest`, `challenge`, `challenge_at`, `challenge_sig`, `session_context`, `stream_id`, and `stream_seq`. `verifier_id` is the v2 key ID selected by the verifier and MUST equal the verifier ID in the authenticated expected challenge. `session_context` is independently null or exactly 32 bytes. `stream_id` and `stream_seq` are both null when unbound, or both set with a 32-byte stream ID and positive safe-integer sequence. The signing projection is every bundle field except `delegations` and `challenge_sig`; it always contains `session_context`, `stream_id`, and `stream_seq`, using JSON null for absence. `delegations` are ordered leaf-to-root and each certificate is v2. `delegation_digest = SHA-384(ASCII("ratify-protocol-delegations-v2") || 0x00 || RatifyCanonicalJSON(delegations))` covers the ordered complete signed certificate objects. The signing projection includes this digest, binding the exact chain to the challenge presentation. The verifier recomputes the digest and rejects mismatch before challenge claim. `challenge` is exactly 32 bytes after base64 decoding. `challenge_at` is copied from the authenticated verifier challenge record, not accepted as proof of issuance by itself. The verifier ID and agent ID must match their complete keys; the agent ID must also match the leaf subject.

The signed challenge-presentation object is exactly the bundle fields `version`, `verifier_id`, `agent_id`, `agent_pub_key`, `delegation_digest`, `challenge`, `challenge_at`, `session_context`, `stream_id`, and `stream_seq`. It excludes `delegations` and `challenge_sig`. The agent signs it using code `0x0002`. A verifier MUST provide an authenticated expected challenge record containing challenge bytes, issuance time, expiry, verifier namespace, rollback-protected replay epoch, verifier key ID, optional expected agent ID and complete public key, optional `expected_receiver_id`, and optional 32-byte `expected_session_context`. Before claiming replay state, the verifier validates the proof's structure, key and chain linkage, all certificate and challenge signatures, exact challenge bytes and timestamp, pure local receiver binding, and configured freshness. It performs no trust-domain membership fetch or other external lookup before claim. Trust-root resolution, issuer-status lookup, audience membership, and authorization policy happen only after the challenge claim succeeds, as specified in §6. The claim is atomic across concurrent requests. A locally issued challenge is trusted because the caller owns its issuance state; a remote challenge requires an independently authenticated issuer and audience binding. A proof bundle alone cannot prove that its challenge was issued by the intended verifier.

### 5.3 Revocation objects

Status-key binding is issuer-scoped state but key material is globally role-separated: a status key ID and each component public key MUST be unique across all issuers' status roles and distinct from every non-status key component admitted by local trust configuration or present in an evaluated chain. This is a permanent role assignment: a key ID or component public key ever used for a status role, including a retired status key, MUST NOT later be admitted as a delegation, rotation, verifier, witness, receiver, or other non-status role; a key ID or component ever admitted for a non-status role MUST NOT later become a status key. The verifier deployment maintains append-only role history for every complete key ID and both component public keys, including retired bindings, and rejects cross-role reuse during configuration load and verification. Status-key epoch numbers strictly increase per issuer and MUST never be reused. The rollback-protected security journal MUST retain global key-role history, each issuer's status-key binding history and epochs, `deny_union`, accepted floors, and authenticated observations; restore or reconfiguration cannot erase this history.

`RevocationList` required fields are `version`, `issuer_id`, `updated_at`, `next_update`, `sequence`, `revoked`, `signature`. `sequence` is a positive safe integer and monotonically increasing revocation-set version per issuer and locally configured status-key epoch. A status-key replacement is accepted only through caller-authenticated trust configuration, starts a strictly greater epoch, and MUST use a key ID and component key material never previously bound to any status key in the verifier deployment. Rebinding a retired status key is prohibited. The complete status public key and each Ed25519/ML-DSA component MUST satisfy the global role-separation rule in §5.3, including across issuers and all admitted non-status roles; the complete key must also differ from every issuer or subject key in the evaluated chain. The rollback-protected history is global to the verifier deployment, not scoped only to this issuer. The verifier checks this binding when trust configuration is loaded and again before applying each StatusResult, even though the provider callback receives only CertificateRef. The trust-configuration transition MUST carry forward the complete prior-epoch `deny_union` and any signed final status checkpoint available to the operator; unseen old-epoch objects first received after cutover are rejected and cannot add revocations. On transition, discard the prior epoch's `accepted_set`, accepted snapshot, and floor; reset `max_observed_sequence`, `fork_sequence`, and reconciliation flags; retain issuer-wide `deny_union` and authenticated observation digests. Until a fresh snapshot under the new key bootstraps the new epoch and contains the retained `deny_union`, status is unavailable. Objects signed under the retired status key and first received after the trust-configuration epoch transition are no longer authenticated status input: reject and alert on them, and do not add their contents to `deny_union`. Retain prior-epoch deny witnesses and compact sequence/equivocation markers; full prior-epoch objects need not remain in the hot status journal after their authenticated digests and certificate witnesses are recorded. They MUST NOT change current-epoch accepted state, floor, or sequence. A verifier with no stored floor MAY bootstrap from a fresh, authenticated full snapshot only when its sequence is at least the highest sequence of any authenticated push or snapshot already observed in the current status-key epoch and its revoked set includes all observed valid revocations from the current epoch whose observed sequence is no greater than the snapshot sequence. Two authenticated full snapshots at the same sequence with different revoked sets are a fork even before bootstrap; the same rule applies to two authenticated pushes at the same sequence with different signed bodies. A first snapshot in a new epoch MUST also include the retained issuer-wide `deny_union` from prior epochs. Otherwise bootstrap remains pending as an unavailable gap, not a fork: the new key has not contradicted a current-epoch status object. A later fresh snapshot at a higher sequence must carry the retained deny union before status can become current; a corrected set at the same sequence is a fork. `updated_at < next_update`; `next_update - updated_at` MUST NOT exceed the verifier's configured maximum list lifetime. The verifier MUST configure a finite maximum list lifetime and a finite maximum age for accepted status state; status is unavailable when either bound is not configured. `revoked` is an array of unique `{cert_id}` references; the issuer namespace is supplied by the signed `issuer_id`, so a reference is `(issuer_id, cert_id)`. The signable projection is every field except `signature`. The list is signed with code `0x0003` under a status key that caller-authenticated configuration binds to this exact issuer ID and status role before sequence or freshness state changes. The complete status public key MUST differ from the issuer delegation/rotation signing key and every agent key in the chain; status-key role separation is mandatory. The verifier stores (1) `accepted_set`, from the last accepted full snapshot plus contiguous accepted pushes; (2) `deny_union`, the union of every validly signed revocation observed, including stale, future-dated, out-of-order, or forked objects; (3) a compact authenticated status index: one earliest-sequence witness per certificate in `deny_union`, the accepted full-snapshot base, every accepted contiguous push after that base, and compact sequence/set/body digests needed for replay and equivocation checks. Keep full revoked-reference arrays only for the accepted base, accepted contiguous pushes, and currently unresolved reconciliation evidence. Redundant heartbeats MUST NOT cause storage to grow with heartbeat count or repeat the complete deny union. Retain compact fork markers after recovery so replaying an already reconciled fork cannot freeze status again; (4) `max_observed_sequence`; (5) `fork_sequence`, initialized to 0 and meaningful only while a fork is unresolved, equal to the highest accepted floor or object sequence implicated in that fork; and (6) `reconciliation_required` for gaps, forks, future timestamps, or revocations not represented in accepted state. A fresh snapshot at sequence S MUST include every observed valid revocation in the current status-key epoch with observed sequence <= S. It need not include current-epoch observations with sequence > S, but cannot clear `reconciliation_required` or support `not_revoked` until sequence S is at least `max_observed_sequence`, the snapshot is fresh, and it includes all `deny_union`. Omission of a revocation observed at or before S is equivocation and a fork. A snapshot below the floor cannot advance freshness or floor. A fresh snapshot with `floor < S < max_observed_sequence` may replace `accepted_set` and advance the floor to S only if it includes all observed current-epoch revocations through S; it leaves reconciliation pending and cannot produce `not_revoked`. If it omits such a revocation, it is a fork. If a snapshot below the floor contains a revocation absent from the accepted cumulative set at the current floor, add it to `deny_union`, record the observation, declare a fork, alert, and require reconciliation; the signed lower-sequence claim contradicts the accepted later state. Classify an incoming snapshot against the accepted state before attempting reconciliation. With no reconciliation pending, a fresh full snapshot above the floor is accepted when its sequence is at least `max_observed_sequence`, its revoked set includes every current-epoch observation through that sequence and all retained `deny_union`, and it has no same-sequence conflicting observation. It replaces the accepted snapshot and set and advances the floor. A non-fresh snapshot never advances accepted state or freshness and is recorded as an authenticated observation. Replaying a previously recorded fork marker after a fresh snapshot has reconciled it MUST NOT reopen reconciliation. Exact replay of other already processed evidence is idempotent. A snapshot first observed as future-dated may be re-evaluated when its timestamp is no longer future and the full freshness bounds pass; after acceptance, further replays are idempotent. A non-fresh snapshot with no accepted floor, or with a sequence above the accepted floor, requires reconciliation and makes status unavailable until a fresh snapshot reconciles it. A consistent non-fresh snapshot at or below the accepted floor that omits no revocation observed at or before its sequence and introduces no revocation absent from the accepted cumulative set does not newly require reconciliation; it cannot clear any reconciliation already pending, change the floor, or refresh the accepted snapshot. Any applicable omission or newly observed revocation remains a fork under the rules above. At the current floor, only a snapshot whose revoked set exactly equals the accepted cumulative set is a valid heartbeat; a differing set is a fork and cannot reconcile itself even if it contains `deny_union`. An identical-set heartbeat with `updated_at` earlier than the accepted snapshot is recorded but MUST NOT replace the accepted snapshot or decrease its freshness; otherwise select the heartbeat with greatest `updated_at`, then lowest evidence digest. For every detected fork, set `fork_sequence = max(previous_fork_sequence, current_floor, conflicting_object_sequence)`. Any fork unions all revocations into `deny_union`, freezes status-dependent allows as indeterminate, and raises an alert. For a gap without a fork, a fresh full snapshot at or above `max_observed_sequence` that includes all applicable observed revocations clears reconciliation and becomes the accepted state. A fork can be reconciled only by a fresh full snapshot with sequence strictly greater than `fork_sequence` and at least the current epoch's `max_observed_sequence`, including all of `deny_union`; a same-floor object can never clear a fork. Classification against the current accepted floor takes precedence over reconciliation, so an object cannot be treated as a heartbeat and a recovery snapshot at once. If that sequence cannot be reached or the status key is compromised, recovery requires an independently authenticated status-key replacement in caller trust configuration and a new local status epoch. A new epoch starts with no accepted snapshot, no accepted set, and no stored floor. Reset `max_observed_sequence`, set `fork_sequence` to 0, and clear current-epoch reconciliation flags; retain the issuer-wide `deny_union` and prior-epoch evidence observations. Bootstrap the new epoch only from a fresh snapshot under the new key, and require that snapshot to include the retained deny union. The wire protocol does not define this trust-configuration operation. A full snapshot is fresh only when `updated_at <= now + skew`, `now <= next_update`, and the verifier-configured maximum age passes. An observed future-dated object is not accepted state and makes status unavailable until reconciled. A future-dated snapshot may add its revocations to `deny_union` and its sequence to `max_observed_sequence`, but cannot advance freshness or accepted state.

`RevocationPush` required fields are `version`, `issuer_id`, `sequence`, `pushed_at`, `revoked`, `signature`. Push and full-list snapshots share the issuer revocation-set version within the configured status-key epoch; `sequence` is a positive safe integer. The signable projection is every field except `signature`. A push sequence exactly `floor + 1` may extend `accepted_set` only when its timestamp is not future-dated and no reconciliation is pending; record each added revocation with this sequence and advance the floor atomically. An exact semantic duplicate push body is idempotent even if its randomized signature bytes differ. A nonduplicate push at the current floor or below it may be recorded without changing the floor or `accepted_set` and without requiring reconciliation only when all its revoked references are already in the accepted set and the current accepted full snapshot at or above that sequence omits none of the pushed references. If the push contradicts such a snapshot or introduces a reference absent from the accepted set, it is a fork. Other noncontiguous pushes add their validly signed revocations and sequence to observed state, leave the floor and `accepted_set` unchanged, and set `reconciliation_required`. Its entries are newly revoked cert IDs and use the same issuer namespace. It is signed with code `0x0005` under the authenticated issuer status-key rule. The status key ID and each public-key component MUST be globally unique across every configured status key and distinct from every key ID and component bound to a non-status role in caller-authenticated trust configuration or present in the evaluated chain. This is the deployment-wide role-separation rule in §5.3, not an issuer-local check. A push never refreshes full-list freshness. A future-dated push cannot advance freshness, accepted state, or the floor. An old duplicate is idempotent only when its full signed body matches the stored history for that sequence. A push below the current floor that is not an exact historical duplicate and introduces a revocation absent from `accepted_set` is a fork, because the later accepted cumulative state omits a previously claimed revocation. Other noncontiguous pushes require reconciliation; a gap without evidence of equivocation is not by itself a fork. At an accepted sequence, a full snapshot reconciles the push only when its revoked set exactly equals that sequence's cumulative set; otherwise it is a fork. When a full snapshot and a push for sequence S are both observed, regardless of arrival order or whether reconciliation is already pending, they are consistent only when the accepted set at S exactly equals the set at S−1 union the push's revoked references if the verifier has that checkpoint. If no S−1 checkpoint is retained, the push is consistent only when every pushed certificate is present in the accepted set. In either case, a conflicting push body at S is a fork. This rule applies to epoch bootstrap and to sequence jumps where no S−1 checkpoint exists. Record that push as authenticated, not as an accepted contiguous push, and do not require reconciliation. A pushed certificate absent from the accepted set is a fork; a conflicting push body at S is also a fork. This makes the result independent of whether the snapshot or its represented push arrives first. A different push body at the same accepted sequence is a fork; union its entries and freeze status-dependent allows until a fresh full snapshot reconciles. A fresh snapshot below the current floor cannot roll state back or refresh freshness. Same-sequence identical full snapshots may refresh freshness. Each issuer ID retains its configured status-key mapping after key rotation; rotation to a new derived issuer ID creates a distinct issuer record. It does not move old certificates or their revocation state. A status provider returns `StatusResult` for a `CertificateRef { issuer_id, cert_id }`. Each variant includes `evidence: [StatusEvidenceEntry]`: `{ status: "revoked", evidence }`, `{ status: "not_revoked", evidence }`, or `{ status: "indeterminate", reason: "stale" | "unavailable", evidence }`. `StatusEvidenceEntry` is the exact entry schema defined in §5.6. Providers return a result for every requested reference and MUST NOT throw or omit evidence; a fetch or storage error returns `indeterminate` with reason `unavailable` and an empty evidence array when no authenticated object is available. It returns `revoked` when the pair is in `deny_union`. It returns `not_revoked` only when a fresh, unforked `accepted_set` exists, no gap or reconciliation is pending, its sequence is at least the current epoch's `max_observed_sequence`, it includes the observed deny union at or below that sequence and all retained prior-epoch revocations, and the pair is absent. `unavailable` means the source is unauthenticated or no accepted full snapshot exists, either finite freshness bound is absent, a future-dated object has been observed, or a gap, fork, or reconciliation prevents a current result. `stale` means accepted authenticated status exists but its accepted full snapshot is expired or exceeds the verifier-configured age bound. A provider error with no authenticated status object is `unavailable`. Thus a missing push, pre-bootstrap push, stale conflict, future object, or fork can never produce `not_revoked` while unreconciled.

| Observed state for `(issuer_id, cert_id)` | Result |
| --- | --- |
| Present in `deny_union`, whether or not the feed is reconciled | `revoked` |
| Absent from `deny_union`; no authenticated accepted snapshot, either finite freshness bound is absent, source unauthenticated/unavailable, a future-dated object has been observed, or gap/fork/reconciliation is unresolved | `{status: indeterminate, reason: unavailable}` |
| Absent from `deny_union`; accepted authenticated state exists but its accepted full snapshot is expired or over the verifier-configured age bound | `{status: indeterminate, reason: stale}` |
| Absent from `deny_union`; fresh accepted state covers the highest observed sequence and all applicable observations, with no gap/fork/reconciliation | `not_revoked` |

`revoked` is monotonic for a certificate under one issuer ID. A later snapshot cannot clear a revocation; correction requires a new certificate identity. Issuers MUST NOT reuse a certificate ID for a new authorization.

Status-observation replay is idempotent by `(status_key_epoch, object_type, sequence, semantic_content_digest)`, where the digest excludes the signature and covers the canonical revoked set for a full snapshot or the complete signed body for a push. Retain these semantic markers through compaction. Replaying a previously accepted marker MUST NOT reopen a reconciled fork or alter accepted state. The freshness re-evaluation exceptions are a previously future-dated or stale/gapped full snapshot when it first passes all freshness bounds and is not below the accepted floor, and a same-floor identical-set heartbeat that wins the deterministic freshness tie-break on `updated_at`. Replaying a snapshot below the accepted floor is always a no-op, even if its freshness later becomes valid. A previously forked semantic marker remains a no-op after recovery. Exact signed-object replay is also idempotent, subject to the same freshness re-evaluation exceptions. When checking a newly received push against prior full snapshots, the current accepted snapshot and unresolved snapshots above the accepted floor are authoritative; compacted stale or gap observations below the floor MUST NOT be treated as complete revoked sets or create a new fork.

### 5.4 Key rotation statement

Required fields: `version`, `authority_id`, `recovery_epoch`, `role`, `sequence`, `previous_statement_hash`, `old_key`, `new_key`, `old_key_id`, `new_key_id`, `issued_at`, `not_before`, `old_signature`, `new_signature`. `authority_id` is a stable 32-character lowercase hexadecimal principal handle already bound to the current key by caller-authenticated trust configuration; it is not derived from the replacement key. `recovery_epoch` is a positive caller-authenticated generation. `role` is a closed enum `organization_root`, `issuer`, or `agent`. `sequence` starts at 1 and increments by one within the current epoch. The genesis statement has a 48-byte all-zero `previous_statement_hash`; later statements contain `StatementBodyDigest(0x0004, prior_statement_body)`. Both key IDs are recomputed; old and new keys MUST differ and a new key already present in retained rotation history is rejected. The signable body is every field except both signature fields. The current old key signs code `0x0004`; the new key signs the same body using the distinct code `0x0009` reserved for new-key possession. The new key proof covers both public-key components. This continuity statement has no protocol expiry; relying parties may impose a separate maximum age or approval window without changing the signed object.

This statement proves continuity only. It never establishes trust or causes a generic proof verifier to adopt a key. Initial state is `(sequence=0, head_hash=48 zero bytes, current_key=caller-authenticated genesis key, recovery_epoch=caller-authenticated epoch, used_key_ids={genesis key ID}, forked=false)`. `AcceptRotation(stmt, state, now)` MUST derive the old key exclusively from `state.current_key`, verify both signatures, bind authority, epoch, role and old key ID to that state, require `sequence = state.sequence + 1` and the prior hash equal the stored head, enforce `issued_at <= now + skew` and `not_before <= now + skew`, then atomically store the new head, current key and complete used-key history. Re-evaluation at an already accepted sequence is idempotent only when `StatementBodyDigest(0x0004, body)` equals the stored accepted body digest; new randomized signatures over that same body are the same statement. A different valid body at that sequence is a fork. A detected fork freezes the authority: dependent authorizations return indeterminate until a root-authorized recovery increments `recovery_epoch`, anchors a new genesis to a newly selected key, and preserves the full used-key history. Resetting the sequence without incrementing the epoch is prohibited. Recovery authorization is supplied by the caller's independently authenticated offline-root control plane; this Protocol object does not define organization enrollment or root identity. A v1 key MUST NOT sign or authorize a v2 statement. A compromised current old key can authorize a key it controls; continuity proofs do not detect that compromise. Accepting rotation does not automatically invalidate existing delegations; issuer retirement, old certificate status and verifier trust changes are explicit relying-party policy.

### 5.5 Witness and transaction receipt

`WitnessEntry` required fields are `version`, `log_id`, `sequence`, `prev_hash`, `entry_data`, `timestamp`, `witness_id`, `signature`. `log_id` is a caller-configured stable 32-character lowercase hexadecimal ID unique to a witness log and MUST be covered by the signature. Sequence starts at 1. The genesis `prev_hash` is 48 zero bytes; later values are `StatementBodyDigest(0x0006, previous_entry_body)`. The verifier requires the exact expected `log_id`, next sequence, and predecessor from authenticated log state; gaps, orphans, and cross-log replay are rejected without advancing state. At an already accepted position, the same body digest is idempotent; a different body digest is a fork and permanently freezes that log ID. Recovery starts a new caller-authenticated 32-character lowercase hexadecimal log ID and records an out-of-band recovery link; it does not claim continuity of the frozen log. The signable projection is every field except `signature`. `entry_data` is opaque bytes; `witness_id` MUST equal the v2 key ID of the caller-authenticated witness key. It uses code `0x0006`.

`TransactionReceipt` required fields are `version`, `transaction_id`, `created_at`, `terms_schema_uri`, `terms_canonical_json`, `parties`, `party_signatures`. `terms_canonical_json` is a base64-encoded byte string containing the exact UTF-8 RatifyCanonicalJSON bytes of the application terms, using the restricted Ratify value model in SPEC.md §5.7.1 and canonical byte rules in §§6.1–6.3, including its nesting limit. The complete encoded receipt is limited to `MAX_TRANSACTION_RECEIPT_BYTES` (5 MiB), and `parties` is limited to `MAX_TRANSACTION_PARTIES` (32); decoders enforce both bounds before cryptographic verification. `transaction_id`, `terms_schema_uri`, and each `party_id` MUST be non-empty. Parties are sorted by ascending UTF-8 byte order of unique `party_id` and unique `agent_id` and contain `party_id`, `role`, `agent_id`, `agent_pub_key`, `verifier_id`, `workspace_id`, `session_id`, `invocation_id`, `required_scope`, `proof_bundle_hash`, and `proof_bundle`. A single agent key cannot represent multiple parties in one receipt because that would make separate-party authorization indistinguishable from self-approval. `proof_bundle_hash` is the ASCII text `sha384:` followed by 96 lowercase hexadecimal characters encoding `BundleHashV2`'s 48 digest bytes; see §4. Each signature record contains unique `party_id` and `signature`; its party ID must occur in the parties list. Signature records are sorted by ascending UTF-8 byte order of `party_id`. Every party signs the same signable object: `version`, `transaction_id`, `created_at`, `terms_schema_uri`, `terms_canonical_json`, and the sorted parties with all fields except `proof_bundle`. The `proof_bundle` bytes and `party_signatures` are excluded. Every listed party must have exactly one valid signature. `role`, `session_id`, and `invocation_id` MUST be non-empty valid UTF-8 strings. All signatures use code `0x0007`. A verifier MUST check `proof_bundle_hash == BundleHashV2(proof_bundle)` before verifying the bundle, and reject a mismatch. It checks each included bundle against configured trust and status sources and requires bundle agent ID, public key, and leaf subject to match the signed party. It computes `transaction_context = SHA-256(ASCII("ratify/transaction-context/v2") || lp(transaction_id) || lp(terms_schema_uri) || SHA-384(terms_canonical_json))`, then `transaction_party_request_hash = SHA-256(ASCII("ratify/transaction-party-request/v2") || lp(transaction_context) || lp(required_scope))`; for that party it recomputes `session_context` using the signed `verifier_id`, `workspace_id`, `agent_id`, `session_id`, and `invocation_id` plus this request hash, then requires equality with the bundle context. Scope is evaluated against the signed `required_scope` and the included delegation chain. This prevents attaching a valid bundle from an unrelated action or scope. A verifier without a trusted challenge issuer or current status can establish signatures and chain structure only; it MUST report freshness and current authorization as unknown, not claim these were verified. The protocol does not interpret application terms; applications MUST define a versioned schema URI and use canonical JSON terms.

### 5.6 Verification receipt

Required fields: `version`, `log_id`, `sequence`, `verifier_id`, `bundle_hash`, `issuer_ids`, `decision`, `decision_reason`, `identity_status`, `trust_assessment`, `status_assessment`, `challenge_assessment`, `context_assessment`, `context_policy_digest`, `verified_at`, `required_scope`, `granted_scope`, `status_evidence_digests`, `previous_receipt_hash`, `signature`. `log_id` is a stable caller-configured 32-character lowercase hexadecimal identifier, unique and never reused. Sequence starts at 1 and increments contiguously per log. `decision` is exactly `allow`, `deny`, or `indeterminate`. `decision_reason` is one of `authorized`, `not_delegated`, `delegation_not_authorized`, `delegation_expired`, `delegation_revoked`, `scope_denied`, `constraint_denied`, `constraint_unverifiable`, `constraint_unknown`, `invalid_scope`, `proof_invalid`, `unauthorized`, `status_stale`, `status_unavailable`, `action_context_unverified`, `trust_unavailable`, or `evaluation_interrupted`. `identity_status` is one of `authorized_agent`, `expired`, `revoked`, `scope_denied`, `invalid_scope`, `constraint_denied`, `constraint_unverifiable`, `constraint_unknown`, `delegation_not_authorized`, `authorization_unverified`, `invalid`, or `unauthorized`. `trust_assessment` is exactly `trusted`, `untrusted`, `unavailable`, or `not_evaluated`; `status_assessment` is exactly `current`, `revoked`, `stale`, `unavailable`, or `not_evaluated`; `challenge_assessment` is exactly `current` in a terminal receipt; `context_assessment` is `bound`, `not_required`, `unbound`, `unverified`, `mismatch`, or `not_evaluated`. `mismatch` records a post-claim Protocol context-policy mismatch only when that policy is supplied as Protocol verifier context; it is a `deny` with `constraint_denied` and identity status `constraint_denied`. In managed Verify, the authenticated receiver/action/session binding is checked by the pure pre-consumption hook; a mismatch is a preflight failure with no Protocol claim or receipt. `context_policy_digest` MUST be null if and only if no context policy was configured or `context_assessment` is `not_evaluated`; otherwise it MUST be the lowercase `sha384:` digest of the locally configured context policy used for this decision. Verify MUST configure the fixed `ratify.verify.session-context/v1` policy defined in §6.1 and MUST provide the authenticated expected session-context value from challenge issuance; a matching value yields `context_assessment: bound`. A configured policy digest is included when its result is `unverified` or `mismatch`. `verifier_id` MUST equal the v2 key ID of the caller-authenticated verifier key. `issuer_ids` is the sorted unique list of every certificate issuer ID in the proof chain. `status_evidence_digests` is the deduplicated union of the evidence entries returned for every chain `CertificateRef`. Each entry has exactly these fields and JSON types: `{ "issuer_id": <64 lowercase hexadecimal characters>, "status_key_id": <64 lowercase hexadecimal characters>, "sequence": <positive safe integer>, "object_type_code": <integer>, "digest": <string> }`. `object_type_code` is only integer `3` (`0x0003`, `RevocationList`) or integer `5` (`0x0005`, `RevocationPush`). `digest` is `sha384:` followed by exactly 96 lowercase hexadecimal characters and is the textual encoding of `StatusEvidenceDigest` over the exact complete signed object, including its signature. `issuer_id`, `status_key_id`, and `sequence` MUST identify the exact signed object and caller-authenticated status key whose digest is supplied. `object_type_code` MUST equal both the `code` argument to `StatusEvidenceDigest` and the schema code assigned to that object. Every entry issuer MUST be a member of `issuer_ids`. No extra fields are permitted. Entries are unique by the five-field tuple and sorted by ASCII `issuer_id`, ASCII `status_key_id`, numeric `sequence`, numeric `object_type_code`, then ASCII `digest`, ascending. For `allow`, `status_evidence_digests` MUST contain at least one entry, and every chain `CertificateRef` MUST return `not_revoked` with evidence including the accepted full-list digest and any contiguous accepted pushes after that list, `trust_assessment` is `trusted`, `status_assessment` is `current`, `challenge_assessment` is `current`, `context_assessment` is `bound` or `not_required`, and `context_policy_digest` is present. An archival proof or a proof with unbound context and no explicit `not_required` context policy can never have `decision: allow`. A verifier that validates a receipt alongside its proof bundle MUST check that `issuer_ids` exactly match the bundle chain and `verifier_id` equals the bundle `verifier_id`; a receipt without the bundle is only the caller-authenticated verifier's signed assertion. `allow` requires identity status `authorized_agent`, reason `authorized`, `trust_assessment: trusted`, status `current`, and the evidence and context requirements above; `granted_scope` is the effective scope. `deny` has empty `granted_scope` and uses the deterministic reason/status pairs: `not_delegated` with `delegation_not_authorized`; `delegation_not_authorized` with `delegation_not_authorized` for a nonempty chain; `delegation_expired` with `expired`; `delegation_revoked` with `revoked`; `scope_denied` with `scope_denied`; `invalid_scope` with `invalid_scope`; `constraint_denied` with `constraint_denied`; `constraint_unverifiable` with `constraint_unverifiable`; `constraint_unknown` with `constraint_unknown`; `proof_invalid` with `invalid`; `unauthorized` with `unauthorized`. `indeterminate` requires identity status `authorization_unverified`, empty `granted_scope`, and one of `status_stale`, `status_unavailable`, `action_context_unverified`, `trust_unavailable`, or `evaluation_interrupted`. The required assessment tuple for each indeterminate reason is defined by the table in §6. Expired or unverified challenge freshness is a pre-claim failure and MUST NOT appear as `challenge_assessment: freshness_unverified` in a terminal receipt. All dimensions whose check was not reached MUST be `not_evaluated`; earlier successful dimensions retain their actual assessment. `trust_unavailable` requires `trust_assessment: unavailable`; a trust configuration that was available but rejects the chain is a deny with `unauthorized` and `trust_assessment: untrusted`. `required_scope` is one non-empty canonical scope string, never a wildcard or `custom:` string. Optional `agent_id` is the bundle agent ID. Optional `human_id` is caller-authenticated association metadata, included only when the caller has an independently trusted human-to-key mapping; it is not established by the proof or receipt alone. When present, `human_id` is a non-empty valid UTF-8 string carrying the caller's opaque identity value; implementations do not normalize it, and the receipt wire-size limit bounds its length. Optional `agent_id` is a 64-character lowercase hexadecimal v2 key ID. `bundle_hash` is `BundleHashV2`. The genesis previous hash is 48 zero bytes; subsequent links are `StatementBodyDigest(0x0008, previous_receipt_body)`. The optional `agent_id` and `human_id` fields are included in the signable body when present; absence does not imply a value. The signable body contains exactly all required fields except `signature`, plus those optional IDs when present, and no unknown fields. Receipt verification requires caller-authenticated verifier key and expected log ID, expected sequence, and prior head; it never trusts a key embedded in a receipt. Caller-authenticated log state pins one verifier ID for the lifetime of a log. Verifier-key rotation drains the receipt outbox and starts a new log ID under the new verifier ID. At an already accepted sequence, an identical body digest is idempotent; a different body digest is a fork that permanently freezes that log ID. Recovery starts a new caller-authenticated log ID and records an out-of-band recovery link without claiming continuity. Verify under code `0x0008`.


The JSON wire types and encodings for this receipt are normative: `version`, `sequence`, and `verified_at` are integers; `verified_at` is Unix seconds. `log_id` is a 32-character lowercase hexadecimal identifier; `verifier_id` is a 64-character lowercase hexadecimal v2 key ID. `bundle_hash` is `sha384:` followed by 96 lowercase hexadecimal characters and encodes `BundleHashV2`. `issuer_ids` is a sorted array of 64-character lowercase hexadecimal v2 key IDs. `required_scope` is one canonical scope string. `granted_scope` is a sorted unique array of registered canonical scopes or valid exact `custom:` extension scopes, contains no wildcard, and is empty for deny or indeterminate. `context_policy_digest` and status-evidence `digest` use the prefixed lowercase hexadecimal form. `previous_receipt_hash` is base64 of the 48 raw bytes returned by `StatementBodyDigest`; genesis is base64 of 48 zero bytes. `agent_id`, when present, is a 64-character lowercase hexadecimal v2 key ID. `human_id`, when present, is a non-empty valid UTF-8 string preserved without normalization. `signature` is the Protocol v2 `HybridSignature` object with exactly `ed25519` and `ml_dsa_65`, each base64-encoded. The signable body is exactly these JSON fields and encodings under `RatifyCanonicalJSON`.

An appended receipt is immutable historical evidence of Protocol evaluation, even when a managed Verify result is withheld. A receipt by itself does not prove that a Verify result was released or that a receiver executed an action. Managed Verify MUST retain the complete chained receipt log for audit, expose only its checkpoint-acknowledged prefix, restrict access to entries for withheld results to separately authenticated and authorized auditors, and expose receipts through ordinary decision or receipt APIs only for released results. A receiving SDK MUST require an authenticated Verify release response and independently check expiry and receiver-local authorization gates before a handler side effect; possession of a Protocol receipt alone is insufficient.

### Receipt wire encoding

The receipt is serialized as a strict JSON object with no unknown fields. `version`, `sequence`, and `verified_at` are integers; `verified_at` is Unix seconds. `log_id` is a 32-character lowercase hexadecimal log identifier. `verifier_id`, every `issuer_id`, and each status `status_key_id` are 64-character lowercase hexadecimal v2 key IDs. `bundle_hash` and non-null `context_policy_digest` use the `sha384:` prefix followed by 96 lowercase hexadecimal characters. `issuer_ids` is sorted and unique. `required_scope` is one canonical non-empty scope; `granted_scope` is a sorted, unique array of registered canonical or valid exact `custom:` extension scopes, contains no wildcard, and is empty unless the decision is `allow`. `previous_receipt_hash` is base64 encoding of exactly 48 bytes; the genesis value is 48 zero bytes. `agent_id`, when present, is a 64-character lowercase hexadecimal v2 key ID; `human_id`, when present, is a non-empty valid UTF-8 string preserved without normalization. `signature` is a hybrid signature object with base64 `ed25519` and `ml_dsa_65` members. Status evidence entries are unique and sorted by `(issuer_id, status_key_id, sequence, object_type_code, digest)`. These encodings are normative and shared by every SDK.

## 6. Verifier requirements

A live Protocol `VerificationReceipt` is emitted only after the input has decoded to a complete v2 `ProofBundle`, `BundleHashV2` and `issuer_ids` can be computed, `required_scope` is a valid canonical scope, all cryptographic and freshness prechecks pass, the receiver-binding hook passes when configured, and the challenge claim succeeds. Bounded decode, unsupported-version, incomplete-shape, structurally malformed certificate, invalid-request-scope, invalid-signature, stale-challenge, or receiver-binding failures occur before receipt generation; an application may record them as separate transport/preflight audit events but MUST NOT label them Protocol receipts. A certificate with valid wire structure and a valid signature but an empty, duplicate, unregistered, wildcard, or otherwise invalid v2 scope is evaluated after claim and produces the `invalid_scope` receipt result in the table.

The verifier MUST execute in this order. First, perform bounded strict decode, version/object-shape validation, and canonical `required_scope` validation; recompute every key ID, check `delegation_digest` and chain linkage, and reject any repeated exact `(issuer_id, cert_id)` `CertificateRef` in one chain as a structural preflight failure; the same `cert_id` under different issuers is valid and remains issuer-scoped. Then verify all certificate signatures and the challenge signature using the keys in the decoded chain. For an empty `delegations` array, verify `challenge_sig` with the bundle agent key. Do not resolve a trust root or call a status provider in this phase. Next, validate the authenticated `ExpectedChallenge` against the locally configured verifier namespace and rollback-protected replay epoch, challenge bytes, issuance time, and verifier ID, then check its expiry and maximum age. Run the application profile's pure local receiver-binding pre-consumption hook over the verified presentation, authenticated `ExpectedChallenge` record (including its expected agent binding when present), and immutable local receiver/action configuration, including any required receiver, action, invocation, and session bindings. A Verify profile MUST bind the expected agent identity at challenge issuance; a claimed identity is only a matching constraint and does not establish trust. If any chain link has `ratify.receiver_audience`, `expected_receiver_id` MUST be present. The hook MUST reject before claim only when an exact-only audience on a chain link excludes that receiver. Where a link also names trust domains, exact-ID mismatch alone MUST NOT reject; domain membership is evaluated after claim. The hook performs no I/O, trust discovery, status lookup, policy decision, billing, or other side effect. It MUST NOT fetch or resolve trust-domain membership before claim. If any pre-consumption check fails, do not consume challenge or stream state and do not invoke trust, status, custody, authorization, or policy callbacks. Such failures are transport/preflight audit events, not `VerificationReceipt` objects.

### Challenge preflight and claim lifecycle

Every request, including an exact retry, MUST repeat bounded decoding, structural checks (including rejection of a repeated exact `(issuer_id, cert_id)` pair), signature verification, challenge freshness checks, and the configured pure local receiver-binding hook before looking up or returning a stored claim result. These checks do not resolve trust roots or call external status providers. A duplicate exact certificate reference is a pre-claim structural failure with no claim, Protocol `VerificationReceipt`, or billable result; the same `cert_id` under different issuer IDs remains valid. Claim lookup through proof submission MUST NOT reveal whether a claim exists or return its result until this preflight passes; a separately receiver-authenticated management read by an already known claim ID is outside this proof-submission rule.

Before claim, the verifier MUST retain the authenticated challenge issuance record through `expires_at` so an unexpired exact retry can complete preflight. Requests received at or after expiry fail preflight and cannot retrieve a stored result; the claim record remains as a replay tombstone through its retention period. The stable claim ID is `lowercase_hex(SHA-256(ASCII("ratify-protocol-claim-id-v2") || 0x00 || lp(UTF8(verifier_namespace)) || uint64_be(replay_epoch) || ChallengeClaimDigest(challenge)))`, a 64-character lowercase hexadecimal string independent of proof digest. After pre-consumption checks pass, atomically create a claim whose unique key is `(locally_configured_verifier_namespace, replay_epoch, ChallengeClaimDigest(challenge))`; store `BundleHashV2` of the complete strictly parsed bundle, including all signatures, as the immutable claim value, not as part of the uniqueness key. The claim record MUST also seal the bundle's authenticated `agent_id`, required scope, context-policy digest, sorted issuer-ID set, verifier ID, freshness bounds, and optional stream ID and sequence. `BundleHashV2` is computed over `RatifyCanonicalJSON` of that bundle. A retry must use the identical signed bundle; re-signing changes the digest and is rejected as replay. Claim creation, challenge consumption, and any stream-sequence advance keyed by `(namespace, agent_id, stream_id)` are one transaction. Inside that same transaction, the claim store MUST recheck the challenge expiry and configured maximum-age boundary using its authoritative time source and reject if the challenge is no longer fresh. The same authoritative time source MUST govern claim garbage collection; expiry checking MUST NOT be done only before the transaction. The claim store MUST be durable for the deployment replay domain. An exact retry with the same proof digest may retrieve only that claim's released terminal result and MUST be marked as a replay. Protocol does not execute handlers; a managed Verify receiver MUST use a separate durable action-idempotency claim and MUST NOT start the action again on a replay. A different proof digest for an already claimed challenge is rejected as replay, MUST NOT retrieve the first proof result, MUST NOT start another decision, and creates no second Protocol receipt.

The atomic creator receives one unpredictable, per-claim evaluator capability; exact retries, including retries of terminal but unpublished claims, receive none. Durable stores MUST retain only a one-way cryptographic hash of this capability and MUST compare it during terminal finalization, or during an externally anchored attempt preparation as specified below, together with the claim state and unexpired evaluation lease. Possession of a claim ID alone is never authority to finalize. The capability is issued only once to the atomic claim creator and is never returned on a retry. A failed preparation rolls back without creating an attempt. Under the same unexpired evaluator lease the capability may authorize another prepared attempt after such a rollback, or after a definitive external conflict and fresh evaluation against the new anchored head; it never authorizes a second terminal outcome. Recovery after lease expiry is a separate claim-store compare-and-set transition, or an externally anchored interruption barrier as specified below, limited to `indeterminate / evaluation_interrupted`; it cannot replace a terminal result. Finalization MUST bind the unsigned receipt body to the claim's sealed verifier ID, agent ID, bundle hash, sorted issuer IDs, required scope, and context-policy digest, and MUST reject malformed or mismatched decision/reason values. An unreleased terminal claim remains hidden as a terminal replay even after signed receipt append and independent checkpoint acknowledgement; the claim store MUST expose its terminal result only after all release predicates pass.

The receipt outbox body prepared before terminal commit MUST contain exactly the required receipt fields other than `log_id`, `sequence`, `previous_receipt_hash`, and `signature`, plus `agent_id` and `human_id` when present. It MUST use canonical Ratify JSON and satisfy every receipt decision, assessment, scope, and evidence rule before the terminal commit point; the verifier MUST also bind its fields to the authenticated claim, proof bundle, status evidence, configured context policy, and evaluated result. Before commit, it MUST also prove that adding the maximum-size canonical log fields and v2 hybrid signature keeps the complete receipt within the receipt wire-size limit. Terminal commit seals the exact body bytes. At ordered append, the publisher assigns the log fields, signs, decodes and verifies the complete receipt, removes only those four fields, and requires the resulting canonical body bytes to equal the sealed outbox body. Retries reuse the identical sealed bytes.

### Rollback-resistant state and recovery

Managed Verify MUST maintain one append-only security-state journal per stable logical replay domain, not per process. It covers challenge issuance, replay claims, stream sequence, approval nonce use, receipt outbox and log state, and recovery epoch. The receiving service maintains its action-idempotency ledger in its own journal and MUST protect it with its own independent checkpoint; the Verify checkpoint does not cover receiver-local state. Each checkpoint is in a failure domain separate from the state it protects and stores stable `runtime_id`, its role-specific epoch, `security_state_sequence`, hash-chain digest, and digest of the complete security state at that sequence. Verify uses `verify_replay_epoch`, and Protocol `replay_epoch` equals this Verify-owned value. The receiving service uses a separate `receiver_recovery_epoch`; Verify epoch changes do not advance or replace it. A checkpoint is itself monotonic and MUST NOT be restored or asynchronously failed over to an earlier epoch, sequence, or digest. Its monotonic head MUST be protected by a non-restorable anchor. If the checkpoint is rebuilt, restored, or cannot prove its current head, the affected runtime stays `recovering` until its separately pinned recovery authority advances that runtime's anchored epoch. A Verify recovery rejects earlier-epoch challenges; a receiver recovery rejects earlier-epoch approvals, invocations, and action bindings. A database or checkpoint snapshot cannot serve as that recovery authority. In managed Verify, Protocol `replay_epoch` is `verify_replay_epoch`; it is distinct from `receiver_recovery_epoch`, Protocol key-rotation epochs, and issuer status-key epochs. Each durable security-state transaction advances the sequence and hash chain. Hash-chain entries use `SHA-256(ASCII("ratify-security-state-journal-v2") || 0x00 || prior_hash || uint64_be(sequence) || RatifyCanonicalJSON(journal_entry))`; genesis `prior_hash` is 32 zero bytes. The complete-state digest is `SHA-256(ASCII("ratify-security-state-snapshot-v2") || 0x00 || RatifyCanonicalJSON(complete_state_projection))`, where the versioned projection contains all durable security records in canonical primary-key order. Garbage collection, expiry, tombstoning, and other time-driven changes are journaled state transitions with their authoritative decision time; replay never reruns wall-clock-dependent cleanup. The checkpoint accepts only the next sequence with the expected prior digest, except that an identical retry of an already accepted single-entry or group tuple returns its original acknowledgement. Repeating an already acknowledged single-entry `(sequence, hash-chain digest, state digest)` or group `(first_sequence, last_sequence, head_hash, head_state_digest)` MUST return the original acknowledgement; any different tuple overlapping an acknowledged sequence is a fork and freezes the replay domain. A group commit is acknowledged as one tuple `(first_sequence, last_sequence, head_hash, head_state_digest)` after the primary verifies every intervening entry and computes the complete-state digest at the prefix head, and the independent checkpoint receives and checks every intervening journal entry against its acknowledged chain. The primary MUST durably persist the exact immutable group tuple before first submission and MUST NOT recut a pending group after a crash. A lost group acknowledgement is retried with that identical tuple; entries within the prefix are not separately acknowledged. The checkpoint MUST reject an overlapping or sub-range tuple that differs from an accepted group as a fork. A different tuple for an acknowledged range is a fork. No event beyond the acknowledged prefix may be exposed or cause an external effect. Checkpoint unavailability makes that replay domain unavailable by design. A challenge claim is not acknowledged to its caller as consumed, and no in-progress or terminal response for it is returned, until the independent checkpoint has durably acknowledged the claim sequence and its complete-state digest. Before exposing a challenge or approval; returning any response that acknowledges a claim or decision; invoking any external callback; or starting a handler, the primary MUST receive durable acknowledgement for the corresponding complete security-state sequence. If checkpoint acknowledgement is unavailable, do not expose the artifact, run the callback, or start the handler. A primary ahead of the checkpoint may advance it only by replaying and verifying the complete ordered journal from the last acknowledged digest and acknowledging a contiguous prefix through single-entry or group tuples in order; it MUST NOT discard or rewrite unacknowledged state. A primary behind or forked from the checkpoint, an incomplete journal, or a digest mismatch remains `recovering`. A backup, point-in-time restore, or ordinary asynchronous replica is not an independent checkpoint.

The independent checkpoint head and local checkpoint submission or acknowledgement transport records are outside `complete_state_projection`, because they contain or depend on the state digest they acknowledge. A persisted group tuple is immutable and a lost acknowledgement is retried with those exact bytes. Checkpoint submission and acknowledgement transport writes are not security-state journal entries and MUST NOT advance `security_state_sequence`; they are verified against the independent checkpoint, not used as authority themselves. Transport records alone MUST NOT authorize a claim, callback, in-progress response, terminal release, or handler; the independent checkpoint acknowledgement is the authority. The SQL projection head remains in `complete_state_projection` and MUST NOT contain its own state digest or an acknowledgement pointer.

The checkpoint MUST anchor every valid next journal sequence regardless of whether a committed result remains eligible for release. A release failure never rejects or skips a committed sequence. An acknowledgement includes an immutable timestamp from the configured authoritative security clock; exact retry returns the original timestamp, and one group acknowledgement assigns its timestamp to every entry in that group. The complete-state projection contains all primary security records, including profile-defined receiver-floor reports, but excludes checkpoint acknowledgements, their timestamps, and derived release state. Profile-specific release predicates use the committed publication entry, the journal state immediately before it, and its immutable acknowledgement timestamp; they never change checkpoint acceptance of valid committed state.

### Claim finalization and receipt publication

The challenge store, claim state, receipt outbox, receipt-log head, append sequence, `verify_replay_epoch`, and receiver action-idempotency state MUST use their role-specific independent checkpoint contracts above. Verify checkpoint acknowledgement MUST cover a challenge claim before trust, status, custody, or authorization callbacks and the terminal result, signed receipt entry, and advanced receipt-log head before a terminal response. The receiver checkpoint acknowledgement MUST cover its action-idempotency claim before the first handler side effect. The receiver keys that claim by `(receiver_id, workspace_id, authenticated_tenant_id_or_null, operation_id, action_idempotency_id)` and stores the canonical action digest as its immutable value. The caller-stable `action_idempotency_id` is part of the canonical action and approval digest and MUST be reused across fresh challenges for the same intended effect; reuse with the same digest returns the saved outcome or `reconcile_required`, while a different digest is a terminal conflict. Challenge IDs alone are not action idempotency keys. While an effect outcome is uncertain, block reuse of that action ID and any duplicate queued effect until reconciliation establishes the outcome. In a single-store implementation, the terminal transaction reads and advances receipt sequence and prior hash from the acknowledged head atomically with terminal claim and outbox persistence; receipt append and log-head advancement MUST commit in one primary-journal transaction; the independent checkpoint then acknowledges that committed state before any receipt or terminal response is released. These stores do not share a transaction; an unacknowledged committed append is replayed and acknowledged in order as specified above, never discarded or exposed. No alternate storage label or bare high-water counter satisfies this contract. A restore may resume without an epoch change only when the complete ordered journal has been replayed and the primary's sequence, hash-chain digest, and complete-state digest exactly equal the independently anchored checkpoint head. The checkpoint must include every claim, receipt, replay epoch, and action-idempotency record whose callbacks, response, or handler effect were permitted; unacknowledged work MUST NOT have been exposed or cause an external effect. If the Verify checkpoint is ahead and its complete journal is unavailable, freeze affected Verify services and logs; its separately pinned recovery authority advances `verify_replay_epoch`, rejecting every earlier-epoch challenge. If a receiver checkpoint or journal is affected, freeze that receiver and its separately pinned recovery authority advances `receiver_recovery_epoch`, rejecting all earlier-epoch approvals, invocations, and action bindings. Keep each affected runtime in `recovering` with no handler execution until complete action-idempotency state is reconstructed and uncertain effects are reconciled. Never infer that a missing action ID is new. Start a new caller-authenticated receipt log with a recovery link naming the previous log and the anchored checkpoint sequence, hash-chain digest, and state digest. Mark pending unpublished receipt entries in the lost range `receipt_abandoned`; mark any sequence range that may already have been published `published_body_lost`, preserve its signed receipts as historical evidence, and state that the new log does not claim continuity across the missing bodies. Do not label a published receipt abandoned. A stale or forked checkpoint, or a journal that cannot be replayed exactly, cannot resume service. Retain the claim until strictly later than `expires_at + configured_clock_skew`; garbage collection must never make an expired challenge claimable again. Retain its receipt-outbox entry until signed append commits or the receipt log is explicitly abandoned, whichever occurs later; challenge expiry does not discard pending terminal evidence. Any committed terminal result, including `indeterminate`, is sticky for that challenge; recovery requires a fresh challenge. Only one evaluator owns an in-progress claim. An exact retry while evaluation is pending returns an in-progress response without launching callbacks. The evaluator finalizes by claim-store compare-and-set using a fencing token, or durably prepares an externally anchored terminal attempt under that token as specified below. If its lease expires or it fails before terminal commit and no externally anchored attempt remains prepared, recovery commits one sticky `indeterminate` result with reason `evaluation_interrupted`; completed assessments are retained, the active incomplete external lookup is `unavailable`, later checks are `not_evaluated`, and any authenticated status evidence already collected is retained. A late worker cannot replace this terminal result. Lease-expiry recovery never restarts evaluation for that challenge; a fresh challenge is required. For a claim-store terminal commit point, the winning compare-and-set MUST atomically persist the immutable decision and a durable receipt-outbox entry. In that implementation it assigns the receipt sequence and previous-receipt hash while serializing access to that receipt log; an externally anchored implementation assigns these at ordered append from the immutable outbox body. A separate receipt signer may sign only the persisted outbox body; candidate signatures are not exposed as receipts until an append transaction verifies the outbox identity and advances the log head. The append is fenced by claim ID and terminal generation. If signing or append fails, retries process the same immutable body; recovery cannot substitute a different body at that sequence. Later log entries wait for the pending entry to append. No terminal decision or receipt is released to the original caller or any retry until its signed receipt append commits and the independent checkpoint acknowledges that append sequence; until then the API returns an in-progress status after claim acknowledgement unless an expired allow horizon already makes release permanently impossible, in which case managed Verify returns generic `result_withheld`; before claim acknowledgement it returns a generic retryable unavailable response. The receiver cannot run the handler. Before a verifier signing key is retired or rotated, its receipt outbox MUST be drained. If the key is lost, compromised, or cannot sign a pending entry, freeze that receipt log, mark every claim in the abandoned pending sequence range `receipt_abandoned`, and abandon those entries without re-signing any abandoned body under another key. A retry before challenge expiry of an abandoned claim in the unchanged replay epoch receives the non-receipt error `receipt_abandoned`. Abandonment does not erase the terminal Protocol result: for the same `(invocation_id, agent_id)`, a terminal Protocol `allow` or `deny`, including one whose receipt is abandoned, forbids another challenge evaluation; the caller must use a new invocation ID for a new intended action. A terminal Protocol `indeterminate` may be retried within the same invocation using a fresh challenge. A pre-claim failure created no terminal Protocol result and may be retried subject to policy. After expiry, the ordinary expired-challenge preflight rejection applies. If recovery advanced the replay epoch, reject at the earlier stale-epoch preflight check instead. Start a new caller-authenticated log ID with an out-of-band recovery link that names the prior log and last committed head and declares the abandoned pending sequence range without treating those decisions as published receipts; affected claims remain unpublishable and require a fresh challenge under the new verifier identity.

When the terminal commit point is in the claim store, its compare-and-set is the `max_rate` terminal commit boundary. It atomically persists the immutable decision, receipt-outbox body, and a finalization intent binding the claim, exact `CertificateRef` reservations, and terminal outcome. Once this compare-and-set succeeds, lease expiry MUST NOT replace the decision with `evaluation_interrupted`; recovery completes the same reservation commit or release intent and appends the same immutable receipt body. `evaluation_interrupted` applies only when the lease expires before this compare-and-set. If reservation finalization is in a separate store, keep that claim unpublished and in progress until its idempotent intent is acknowledged. The pending receipt sequence blocks later publication in that receipt log, but other claims may evaluate and persist their own outbox entries; none may publish out of sequence. An unrecoverable finalization intent freezes the log and uses the receipt-abandonment recovery procedure. A Protocol `allow` reservation is counted once its terminal compare-and-set commits, even if finalization acknowledgment is delayed. For a terminal `deny` or `indeterminate`, a reservation whose release cannot be confirmed remains capacity-blocking until recovery proves the release; it MUST NOT expire or be assumed released while its outcome is uncertain.

An implementation MAY place the terminal commit point in an independently anchored, linearizable decision log instead of the claim-store transaction, provided its claim and rate-reservation rows can be finalized in one projection transaction. For an evaluator decision, before its external compare-and-set it MUST durably prepare exact event and attempt bytes, expected and next heads, the immutable result and unsigned receipt-outbox body, complete evaluated issuer-status generation vector, allow horizon, and sealed rate batch under the live evaluator lease and fencing capability. An interruption recovery attempt instead requires an expired lease, no unresolved prior attempt, and the exact `indeterminate / evaluation_interrupted` outcome. For an `allow`, preparation MUST check the horizon against the authoritative claim-store clock. The external compare-and-set makes that result immutable; a committed barrier without claim-store projection grants no release. Projection MUST copy the committed result and outbox body exactly and commit or release that attempt's reservations in the same claim-store transaction. It MUST NOT re-evaluate status, horizon, or the expired evaluator lease. Until projection commits, the claim remains in progress and provisional reservations remain capacity-blocking. If a prepared external write is ambiguous, recovery MUST establish the event occupying its exact attempted sequence before projecting it, declaring a definitive conflict, or preparing another outcome. If that sequence is still empty and the exact expected head remains current, recovery resubmits the identical prepared bytes under the same head condition; lease expiry does not invalidate this retry. Lease expiry alone MUST NOT interrupt a prepared or committed attempt. A definitively conflicted attempt may release only its own provisional reservations. While the evaluator lease remains live, its original capability may authorize fresh evaluation against the new anchored head and a new attempt that reserves the same sealed batch again under a new attempt number. After lease expiry, evaluation does not restart; externally anchored `evaluation_interrupted` is committed through its own barrier only after there is no active prepared attempt. Receipt-log sequence, previous hash, and signature are assigned at ordered append from the immutable outbox body. The mandatory signed receipt still appends as historical evidence if the horizon has elapsed. Caller release and receiver handler use MUST withhold that `allow`; a later projection still records the committed Protocol allow, and its `max_rate` reservation remains counted from the provisional reservation timestamp assigned by the authoritative claim-store clock. This option changes neither Protocol v1 behavior nor v2 wire objects.

### `max_rate` reservation finalization

Every provisional reservation is keyed idempotently by the challenge `claim_id` and exact `CertificateRef`. The claim-store terminal compare-and-set, or exact projection of an externally anchored barrier, finalizes all reservations with the immutable Protocol result and receipt outbox: retain/commit them only for Protocol `allow`; release them for every other terminal result, including deny, indeterminate, and `evaluation_interrupted`. A single-store implementation MUST finalize reservations atomically with terminal claim and outbox persistence. An externally anchored implementation MUST finalize them in the exact claim-store projection of its committed barrier, before receipt publication or release. For a claim-store terminal commit point whose reservation store cannot share that transaction, use a durable intent protocol that withholds the terminal receipt and response until reservation finalization is acknowledged; recovery completes the same intent and cannot expose a terminal result with a provisional slot. A later Verify-layer refusal does not undo a Protocol allow or its committed rate count.

### Post-claim trust, status, and policy order

Once claimed, resolve the terminal root against caller-authenticated trust configuration or its explicitly configured trust resolver. Trust resolution MUST use only the already verified chain and locally authorized discovery rules; proof fields MUST NOT select arbitrary network locations or trust roots. If trust cannot be established, commit a terminal `indeterminate` or `deny` result as specified below and do not query issuer status sources. For a trusted chain, evaluate delegation times, scope, context policy, and deterministic constraints that do not reserve rate capacity; obtain a status result for every chain `CertificateRef`; only after all required status results are current may the verifier reserve `max_rate` capacity; Protocol then finalizes its own terminal result and mandatory Protocol receipt. The Protocol result and the Verify result are separate terminal outcomes. Verify `allow` requires Protocol `allow`. Verify may return `deny` or `indeterminate` with any terminal Protocol result when its independent post-Protocol policy or operational checks require that result; this includes `invocation_policy_changed` after the mandatory Protocol receipt has been created. The two post-Protocol operational mappings are exact: a Verify-owned rate-reservation-store outage and a Ratify-operated audience-membership outage that is the sole unverifiable required constraint cause Protocol `deny / constraint_unverifiable` while Verify returns outer `indeterminate`. The Verify result is recorded only in Verify evidence and cannot rewrite the Protocol receipt. A Verify outer `indeterminate` paired with Protocol `allow` or `deny` is final for that invocation and agent; only Protocol `indeterminate` permits a fresh challenge under the same invocation. A pre-claim failure with no Protocol result may retry subject to policy. External Protocol trust and status callbacks run only after the claim; status callbacks are invoked only for a chain whose terminal root has passed trust resolution. A validly signed empty-delegation presentation is claimed and then returns `not_delegated` without trust or status lookup. The namespace supplied by `ExpectedChallenge` MUST equal the locally configured namespace and is never used directly as a storage key. Status callbacks receive `CertificateRef { issuer_id, cert_id }`, never a bare certificate ID. A failed signature or malformed chain MUST produce no external callback. The claim operation must be atomic across concurrent requests in its replay domain. Provider errors return explicit `indeterminate` status and never become non-revoked.

The following table is normative for terminal results after a successful challenge claim. A terminal receipt is appended only by the receipt-outbox finalization path above. A receipt appended after challenge expiry remains audit evidence of the result at `verified_at`; it does not authorize an action after expiry, and an `allow` receipt does not assert that a handler ran. A terminal result is released only after the independent checkpoint durably acknowledges its terminal-result state and the journal sequence containing the signed receipt append and advanced log head, and every profile-specific release predicate passes against that append entry and the journal state immediately before it. The immutable acknowledgement timestamp is the release time and MUST precede authenticated challenge expiry. The claim store and independent checkpoint MUST use the same configured authoritative security-clock source for claim freshness and acknowledgement timestamps; the checkpoint acknowledgement carries a timestamp from that source. If the source is unavailable or cannot be authenticated, publication fails closed. A database commit without checkpoint acknowledgement is not release. If that acknowledgement has not occurred before authenticated challenge expiry, the verifier MUST withhold the terminal result from the caller and return a non-receipt expired-challenge error; it MUST retain the committed Protocol receipt in the restricted complete audit log, but ordinary decision and receipt APIs MUST withhold it. Network delivery can arrive after a pre-expiry release commit, but that delay never extends the challenge or decision action deadline: the receiving application MUST check its authoritative expiry before any side effect. The receiver MUST recheck `now < expires_at` using its authoritative clock and its invocation's pinned recovery epoch against its own durable local epoch inside the action-idempotency transaction before starting a handler. Pre-consumption failures do not create Protocol receipts or consume a challenge; implementations may record them as separate, non-billable audit events. An unexpired exact retry of a claimed proof returns its committed terminal result only after release; after claim acknowledgement, evaluation, receipt append, or publication acknowledgement pending returns an in-progress response. Before claim acknowledgement it returns only a generic retryable unavailable response without claim identifiers. Checks after the claim stop at the first failing row, except that every chain status reference is evaluated once status evaluation begins. Dimensions not yet checked are `not_evaluated`; `not_evaluated` dimensions have no evidence digest. `trust_assessment` becomes `trusted` only after the complete chain validates to the configured root. `status_assessment` is `current` only after every chain `CertificateRef` returns `not_revoked`; a revoked result takes precedence over unavailable or stale results. Preflight MUST seal the exact canonical `required_scope`, proof-bundle hash, sorted unique issuer-ID set, and context-policy digest in the challenge claim record. A policy-less evaluation is permitted only when the verifier explicitly selected a valid policy whose canonical digest records that context is not required. If a post-claim evaluator detects that its in-memory proof or required scope differs from those sealed values before terminal commit, it MUST commit `indeterminate / evaluation_interrupted`; the receipt MUST use the sealed bundle hash and issuer IDs and MUST NOT derive receipt identity from the mismatching input. This is an evaluator failure after claim, not a pre-claim rejection.

For `evaluation_interrupted`, the receipt records only the last non-terminal check state: an interruption before trust resolution has trust `not_evaluated`; interruption during trust resolution has trust `unavailable`; a completed trusted root remains `trusted`; an interrupted status lookup has status `unavailable`; and dimensions not reached remain `not_evaluated`. Context is retained only when its check completed as `bound` or `not_required`. A completed check that would itself produce a terminal allow, deny, or indeterminate result MUST be committed with that result, not replaced by `evaluation_interrupted`. An empty delegation chain may be interrupted before the `not_delegated` result is committed; that receipt has empty `issuer_ids` and trust, status, and context all `not_evaluated`.

The following failures occur before challenge claim and therefore have no `VerificationReceipt`: malformed or unsupported input, invalid/non-canonical request scope, key-ID/digest/linkage failure, malformed certificate structure or invalid certificate/challenge signature, absent/unverifiable/expired/mismatched `ExpectedChallenge`; scope registry, duplicate, empty-list, wildcard, and `custom:*` failures in an otherwise structurally valid signed certificate are evaluated after claim as `invalid_scope`, missing or mismatched expected-agent ID/key or receiver/action/invocation/session binding, or receiver-binding hook mismatch/error. Claim-store unavailability also fails before any trust or status callback and cannot authorize. The claim store is unique by verifier namespace, rollback-protected replay epoch, and challenge digest, with the proof digest stored as the immutable value. A different proof digest for an already claimed challenge is rejected as a pre-claim replay without retrieving the committed result, starting another decision, or emitting a second Protocol receipt. The same proof digest on an exact retry may return the unchanged committed receipt only after release, and a released managed Verify API response MUST expose the stable claim ID and `replayed: true`. Protocol proof-submission retries do not disclose a stored result until the submitted proof passes preflight. A managed Verify deployment MAY provide a separate receiver-authenticated, read-only audit lookup by stable claim ID; that application API does not consume a challenge, rerun Protocol verification, or make an unpublished result available. A receiving service MUST keep its own durable action-idempotency claim before invoking the handler, because a Protocol receipt does not prove or deduplicate an external side effect. The claim and terminal indeterminate result remain durable through challenge expiry plus configured clock skew; recovery requires a fresh challenge.

For managed Verify, checkpoint visibility takes precedence over replay classification after preflight. If a committed claim's security-state sequence is not yet durably acknowledged by the independent checkpoint, an otherwise preflight-valid retry with either the same or a different proof digest MUST receive the same generic retryable unavailable response. It discloses no claim ID, replay flag, in-progress state, result, or receipt, and invokes no trust, status, custody, authorization, or policy callback. The server MAY drive ordered checkpoint catch-up before answering. Once the claim sequence is acknowledged, a different proof digest is rejected as replay and an exact retry follows the in-progress or released-result rules above. A retry received at or after challenge expiry fails preflight before any claim lookup.

Before aggregation, the verifier MUST bind every current and retained historical status-key ID to its issuer using caller-authenticated trust configuration, and MUST reserve every verifier, agent, issuer, subject, and other configured non-status key ID against status-key reuse. Provider evidence cannot establish or modify these role bindings. A result whose evidence key is not bound to its stated issuer is unavailable; it MUST NOT poison another result's role binding. Current and stale evidence MUST use the issuer's current status key; revoked evidence MAY use a retained historical key bound to the same issuer. Digest conflicts are detected across the complete batch independent of input order and make the affected status assessment unavailable. The receipt evidence field is the sorted deduplicated union of structurally valid, role-authenticated returned entries; malformed or unauthenticated provider rows are excluded, and their result is unavailable.

For each chain `CertificateRef`, status results use this precedence: `revoked`; then `unavailable` if no authenticated accepted state, no finite freshness bound, unauthenticated source, future-dated observation, or unresolved gap/fork/reconciliation; then `stale` if accepted state is expired or over age; otherwise `not_revoked`. Across references, `revoked` takes precedence over `unavailable`, which takes precedence over `stale`. The verifier MUST obtain a result for every chain `CertificateRef` even after one result is revoked or indeterminate, and MUST set `status_evidence_digests` to the deduplicated union of every returned evidence array. Evidence selection is deterministic per reference. Treat the absent accepted floor as 0. The accepted base is the full snapshot at the highest accepted snapshot sequence, selecting the one with greatest `updated_at`, then the lowest `StatusEvidenceDigest` in ASCII order. A same-sequence heartbeat never decreases the stored `updated_at` or freshness. For `not_revoked` and `stale`, include that accepted base and every contiguous accepted push after its sequence through the accepted floor. For `revoked`, include those objects plus every stored authenticated observation, including prior-epoch observations retained in `deny_union`, whose revoked set contains the queried certificate. For `unavailable`, include the accepted base and contiguous accepted pushes if present, every stored authenticated current-epoch object with sequence greater than the accepted floor, and every object implicated in the unresolved fork or marked as requiring reconciliation. For an unavailable result with no authenticated object, include no entry. Deduplicate by `(issuer_id, status_key_id, sequence, object_type_code, digest)` and apply the canonical sort order defined in §5.6.

Verification requires `ExpectedChallenge { value, issued_at, expires_at, verifier_namespace, replay_epoch, verifier_id, expected_agent_id?, expected_agent_pub_key?, expected_receiver_id?, expected_session_context? }` from local issuance state or an authenticated challenge issuer. The optional agent fields MUST be supplied together and are authenticated profile data, not values trusted from the proof; the verifier MUST recompute `expected_agent_id` from the complete public key and reject a mismatch before claim. Verify profiles MUST supply both; generic Protocol profiles may omit both. `expected_session_context?` is either absent or exactly 32 bytes. Verify MUST supply the value recomputed from authenticated invocation state, and the verifier MUST require byte equality with the proof `session_context` before claim. `expected_receiver_id` is the stable receiver identifier selected by authenticated local configuration or the authenticated challenge issuer, never by the proof. It MUST be supplied when any certificate has a `ratify.receiver_audience` constraint. `verifier_namespace` MUST equal the configured local replay namespace; `replay_epoch` MUST be an unsigned safe integer from 0 through 2^53−1 and equal the configured rollback-protected current replay epoch; a Verify preflight epoch mismatch produces no Protocol receipt or callbacks and maps to HTTP 409 `stale_replay_epoch`, with no decision result; `verifier_id` MUST equal the caller-authenticated verifier key ID. Before challenge claim, the verifier requires byte equality with the bundle challenge, challenge timestamp, and signed bundle `verifier_id`, then checks expiry and maximum age from the authenticated expected-challenge record. A caller may validate a signature-only archival proof without a current expected challenge, but that offline archival operation is outside the live decision path, MUST be labeled `freshness_unverified`, and MUST NOT authorize a live action or consume live challenge state. If stream fields are present, durable stream state is keyed by `(locally_configured_verifier_namespace, agent_id, stream_id)` and accepts only `stream_seq = last_sequence + 1` (initial sequence 1). Challenge claim, verified proof digest, and stream-sequence advance are one atomic operation. Duplicate, skipped, or reordered turns fail closed. A new stream requires a new stream ID.

For every chain hop, the child issuer key and ID must equal the parent subject key and ID. The terminal root is trusted only through caller-supplied trust configuration. A signature does not create its own trust anchor. V2 uses the Protocol v1 scope vocabulary and exact v1 `ExpandScopes` semantics: canonical scopes and `custom:` scopes remain exact strings; canonical wildcards expand to the registered non-sensitive scopes; wildcards never grant sensitive scopes; `custom:*` is invalid. After claim, every certificate scope MUST pass that closed registry validation before expansion, or verification returns `invalid_scope`. The request `required_scope` is validated before claim and MUST be one non-empty canonical scope, never a wildcard or `custom:` string. Effective scope is the intersection of every certificate's expanded scope set. Verification allows only when the requested canonical scope is a member of that effective scope and all applicable constraints pass. The `ratify.receiver_audience` constraint is evaluated per certificate as specified in §5.1: an exact receiver match OR a valid matching domain membership is required on each constrained link; the chain therefore intersects these per-link results. A valid domain-membership mismatch after claim returns `constraint_denied`; missing or unverifiable required membership returns `constraint_unverifiable`. An exact-only receiver mismatch is the §6 pre-claim rejection with no receipt. Unknown constraint types fail closed. A constraint needing action fields absent from a transaction or request context returns `constraint_unverifiable`; it never passes by omission. For each certificate carrying `max_rate`, after the challenge claim and trusted-root resolution, the verifier obtains complete status for every chain reference. If any reference is revoked or status is unavailable/stale, it finalizes without reserving rate capacity. The challenge claim already seals the canonical reservation batch derived from every signed `max_rate` constraint, without reserving capacity before status is current. It uses that exact sealed batch for reservation. A counter is keyed by `(issuer_id, cert_id, window_s)`, with `CertificateRef` retaining the exact issuer-scoped pair in §5.3. Constraints on the same certificate with the same window share one counter and use the smallest signed `count` limit. The batch has one entry per counter, sorted by issuer ID, certificate ID, then numeric window. `ReserveV2RateBatch(claim_id, owner_token, bundle_hash, batch)` reserves all entries or none in one claim-store transaction using its authoritative clock. A PostgreSQL implementation uses `READ COMMITTED` with one persistent row lock per sorted counter key, then counts active reservations in a separate statement after all locks are held; it rejects a stronger snapshot isolation level unless it implements a proven equivalent with serialization retries. It timestamps the reservation with the database clock after acquiring the locks. For each entry, count committed allows and unreleased provisional reservations whose original reservation time is strictly later than `now - window_s`; reserve only if that count is below the effective limit. A reservation timestamp ahead of the current authoritative clock remains capacity-blocking after clock rollback. The store compares the supplied batch to the immutable batch sealed in the claim. A retry with the same live claim ID and identical sealed bundle hash and canonical batch returns the original provisional reservation and timestamp; changed input is a conflict, never a new capacity check. A terminal or expired-lease claim cannot re-reserve. A provisional reservation has no independent expiry or automatic release: recovery resolves its claim before changing it, and its original timestamp never shifts. The winning terminal claim-and-outbox transaction, or the exact projection of an externally anchored barrier, atomically commits reservations for a Protocol `allow` or releases them for a terminal `deny` or `indeterminate`, including a pre-commit `evaluation_interrupted`; it never leaves a terminal claim with provisional reservations. Post-commit recovery completes the persisted commit or release intent and never unconditionally releases a committed allow. Challenge expiry after terminal commit does not undo the Protocol allow or release its reservation; if Verify withholds response publication because the challenge expired, the receiver handler does not run and Verify creates no billable usage event. A retry under a new invocation for the same intended effect may reserve another `max_rate` slot; this is an intentional consequence of counting Protocol allows rather than handler starts. A later Verify-layer refusal does not rewrite that Protocol result or refund a Protocol invocation; `max_rate` counts Protocol allows, not handler starts. Missing or failed reservation storage yields `constraint_unverifiable`; it never grants by assuming capacity. A Protocol implementation does not execute the downstream handler: `max_rate` counts successful allow decisions, not handler starts. v1 and v2 objects may never be mixed in a chain, bundle, status feed, receipt chain, or API call.

### 6.2 Post-claim status and local-policy precedence

After a successful claim and trusted-root resolution, a verifier MUST obtain and aggregate a result for every chain `CertificateRef` before applying any local authorization-policy denial. This includes a well-formed requested scope that is absent from the effective scope, a known constraint that evaluates false (`constraint_denied`), missing evaluation context (`constraint_unverifiable`), and an unrecognized constraint type (`constraint_unknown`). Implementations MAY evaluate these checks earlier, but MUST retain their outcomes as pending and MUST NOT finalize them before complete status aggregation. The same rule applies to receiver-audience membership mismatches and other post-claim local policy checks.

Protocol verification failures remain eligible to terminate before status lookup: malformed or invalid certificate scope (`invalid_scope`), invalid chain structure or signature, untrusted root, unavailable trust configuration, expired delegation, and missing `identity:delegate` authority. A valid but insufficient effective scope is a local authorization-policy denial (`scope_denied`) and is deferred under the preceding rule. Unknown constraint types fail closed as `constraint_unknown`, after status aggregation. A verifier MUST NOT skip any certificate status lookup because an earlier local policy check failed.

Status aggregation takes precedence over pending local policy outcomes. Any revoked reference yields `deny / delegation_revoked`; otherwise unavailable status yields `indeterminate / status_unavailable`; otherwise stale status yields `indeterminate / status_stale`. Only when every status is current may the verifier apply pending local policy results. Among local results, `scope_denied` takes precedence, followed by `action_context_unverified`, then constraint results. Constraint results use this order: `constraint_denied`, then `constraint_unknown`, then `constraint_unverifiable`. Rate reservation follows current status and passing local policy. Definitive capacity exhaustion produces `constraint_denied`; unavailable or ambiguous reservation produces `constraint_unverifiable`. A verifier whose durable store admits the sealed rate batch atomically with external barrier preparation MAY defer capacity admission to that preparation. If capacity exhaustion definitively rolls back the failing preparation without creating an attempt, and no earlier attempt for the claim remains unresolved or committed, the claimed evaluator may finalize the same claim once as `constraint_denied`; ambiguous preparation never permits changing a fixed terminal payload. No reservation occurs after a non-current status or local-policy denial. Implementations MUST test each precedence case and status completeness across every chain link.

An `allow` finalization MUST carry the earliest authenticated validity horizon of every current status result, every delegation expiry, every accepted receiver-audience membership, and every passing local `time_window`. Status freshness ends at the earlier of signed `next_update` and the configured maximum age after signed `updated_at`. A `time_window` horizon is the first disallowed local minute, capped at the next timezone offset transition; a transition requires fresh evaluation. The durable claim store MUST compare its current database clock with this horizon during the terminal compare-and-set, or during externally anchored attempt preparation, and reject `allow` when the clock is at or beyond it. The verifier MUST use the claim store's authoritative UTC clock for time-sensitive evaluation or shorten the horizon by a configured upper bound on clock skew; an unbounded application/database clock difference can authorize after evidence expires. An unsuccessful claim-store compare-and-set leaves the claim evaluating for lease-expiry recovery as `evaluation_interrupted`, including release of provisional rate reservations. Failed external preparation or a definitive external conflict leaves the claim evaluating; a live evaluator may re-evaluate under its current lease as specified above. After lease expiry, recovery MUST first resolve any prepared external attempt and MUST NOT interrupt an ambiguous or committed one. This check bounds the local decision point. Before releasing any Protocol `allow`, the publication gate MUST compare its immutable checkpoint acknowledgement timestamp with both authenticated challenge expiry and the retained allow horizon. A timestamp at or beyond either boundary withholds the response but does not cancel mandatory signed receipt append. The managed Verify API may return a generic permanent `result_withheld` as soon as this failure is known, even before challenge expiry. The receiver MUST also check the allow horizon, challenge expiry, and its own current authorization gates before any handler side effect. Non-allow decisions carry no allow horizon. The verifier derives this value within the claimed evaluator capability; the database store trusts that application boundary.

The empty-payload operation vector uses the same text fields with no payload digest. Its expected request hash is `7c8898e3e79cee60099a3bfeef03eb641c3e9112130cdc8052f87a20a98567b5`; its resulting session context is `baf54a0c7cb89b813b2bc4b65b2a960dd9a32becb6c3a7c0ad3c3969fabc7aa3`. Both vectors MUST be loaded from the shared fixture and checked by the SDK tests. These vectors and the context-policy/session vector MUST appear unchanged in the shared conformance corpus.

The generic Protocol challenge is opaque and does not itself identify a receiver. An application that needs receiver, tenant, invocation, or action binding MUST define a separately authenticated application profile with its own schema, signature domain, root configuration, audience checks, and exact challenge derivation. Such a profile is not a Protocol v2 object unless it is separately standardized and assigned a registry code. The profile must bind the receiver, trust domain, expected agent ID and complete agent public key, invocation, action digest, nonce, and expiry; its challenge bytes must be recomputed from the exact canonical signed envelope. Verify live receiver profiles MUST bind the expected agent identity at challenge issuance. The pure local pre-consumption hook checks this binding against the verified presentation, so another key cannot consume a challenge issued for that agent. This does not prevent forwarding the intact challenge to the bound agent. The agent SDK accepts it only under a pre-provisioned profile root and configured receiver/trust-domain policy. A challenge response cannot establish its own signing root. The receiver independently validates all receiver-owned binding fields before consuming the challenge. An application may require signed `session_context` derived from its canonical action context. Generic Protocol deployments may use a configured challenge issuer and local audience policy instead. A generic live deployment that omits expected-agent binding MUST keep challenge bytes confidential until presentation and bind delivery to the authenticated intended presenter. If it cannot, anyone who obtains a challenge may consume it with a validly signed proof from an untrusted key, causing denial of service but never authorization; this is an explicit liveness limitation. Verify profiles do not use this unbound mode. Forwarding an intact challenge remains possible if the agent owner has not configured an expected receiver or required human approval; the protocol does not claim to prevent an agent from signing for an unintended but validly challenged receiver.

## 7. External signing and key custody

An implementation may keep private keys in software, a hardware security module, or a provider KMS. The wire contract is independent of custody. An external signer integration qualifies only when it signs the exact SDK-computed `M` with the registered fixed ML-DSA context and passes the vectors; provider labels are not evidence. If using external μ, the KMS is a generic signing oracle and enforcement of allowed type, key role, version, and context belongs to the trusted SDK/signer service and its authorization boundary. There is no requirement for a customer to use AWS or any one cloud provider.

### 6.3 Clarifications recorded during conformance work (2026-10-21)

These resolve ambiguities found while building the shared corpus. Each is normative for v2 and pinned by `testvectors/v2/`.

1. **No context policy.** `VerifyProofBundleV2` may be called with no context policy; the evaluation then reports a null context-policy digest and can never return `allow` (§6 table). A managed verifier that issues challenges MUST configure a policy; the policy-less path exists only for generic callers.
2. **Bootstrap with no stored floor.** A verifier with no stored floor treats the floor as 0 and MAY bootstrap from a snapshot whose sequence is at least the highest authenticated push or snapshot sequence it has already observed; a lower snapshot is rejected. The corpus uses no bootstrap below an observed sequence.
3. **Push before bootstrap.** With an absent floor treated as 0, a push at sequence 1 is `floor + 1` and may extend the accepted set; any higher push before bootstrap is a gap and yields indeterminate status.
4. **Unknown object codes.** The code is derived from the schema being verified, so an unknown code appears only as a signature over another transcript and is reported as `invalid_signature`.
5. **Single-fault precedence.** When several structural faults could apply, a verifier reports them in this order: wire format (`malformed`), key-ID derivation (`key_id_mismatch`), delegation digest, duplicate `CertificateRef`, chain linkage, then signatures. Vectors contain one fault each.
6. **Committed is not released.** A terminal result returned by the live verifier is committed Protocol state, not authorization. A caller MUST NOT release a decision, return a receipt, or let a handler start until the signed receipt append for that claim has committed and the independent checkpoint acknowledges it (§6, "Claim finalization and receipt publication"). The shared corpus does not yet contain stateful publication vectors; each implementation's integration tests must cover this boundary.
