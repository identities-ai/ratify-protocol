# Ratify Protocol v2.0.0-beta.1: internal adversarial review closure record

This record closes the internal adversarial review that SPEC-v2 §8.1 requires
before `2.0.0-beta.1`. It lists every finding rated critical, high, blocker,
medium or low, the commit that addressed it, the test or vector that covers
it, and its status at the commit under review. It also records the exact
package commits and the test results of every SDK.

This is not a security certification. It records what the internal review
found and what was checked. It makes no claim beyond that.

## Scope

In scope: the Protocol v2 specification (`SPEC-v2.md` and Annex A), the shared
vector corpus (`testvectors/v2`, including the cross-SDK fixtures), and the
five v2 SDKs: Go, TypeScript, Python (with its native backend), Rust, and the
C ABI.

Out of scope: the managed Verify service backend, the documentation and
marketing sites, and the reference integrations under `references/`. Their
reviews ran separately and are not closed by this record. Findings from those
reviews are included here only where they concern the protocol, the vectors
or an SDK.

## Method

The review was an **internal adversarial review**: reviewers were asked to
find a way to obtain an actionable decision, a `not_revoked` status, or a
signature that the specification forbids, and to report every defect with a
severity, a location and a fix. It ran in nine rounds between 2026-10-21 and
2026-10-22:

| Round | Subject | Reviewed state |
|---|---|---|
| 1 | Protocol and corpus: the Go live verifier, wire decoding, signing, status, rotation and logs, and whether the corpus could detect a wrong implementation | early Go reference |
| 2 | Alpha publication readiness, then a re-review of the fixes | `2.0.0-alpha.1` candidate |
| 3 | Specification against the Go reference | early Go reference |
| 4 | The v2 design decisions (normative layers, SDK scope, journal, status provenance, release, numbers and clocks, limits, API shape, ordering, beta gates) | decision record and Go reference |
| 5 | v1 capabilities missing from v2 | `6bf011f` |
| 6 | Go reference freeze, four passes, each re-reviewing the last | `6bf011f`, `c8719ff`, then to `aa4855d` |
| 7 | Per-SDK review of C, Python, Rust and TypeScript | `61133f3` |
| 8 | Per-SDK confirmation of every round 7 fix, plus a fresh hunt for new high or critical issues, in Go, C, Python, Rust and TypeScript (TypeScript twice) | `a51b24e`, then `b6aed4d` and `55e6a20` for TypeScript |
| 9 | End-to-end: specification and corpus against every SDK, and the public documentation in this repository | `873827f` |

There was no separate Go-only pass in round 7: the Go reference was the
subject of rounds 1, 3, 4 and 6, and of the Go confirmation pass in round 8.

**Closure verification.** For this record every finding was traced to its
fixing commit with `git log`, `git log -S` and `git log --grep`, and the fix
was read in the code at `efb7f12`. For 25 fixes the fix was reverted
temporarily, the covering test was run and seen to fail, and the fix was
restored; nothing was committed during these checks and the tree was
confirmed unchanged afterwards. TypeScript and Python checks ran on an
exported copy of `efb7f12`. The results are in
[Regression checks](#regression-checks).

**Re-review.** SPEC-v2 §8.1 requires each critical and high fix to be
re-reviewed. The table names the round that re-reviewed each one. Where it
says "closure verification", the only re-review is the verification done for
this record; no later review round examined that fix.

- **OPEN.** Findings 56 and 57 are release steps that must be done at the tag
  (`docs/RELEASES.md` step 6a). They are not code defects, but the beta must
  not be tagged until both are closed.
- **Critical and high findings without a separate re-review round.** Findings
  52 and 53 (high) were fixed after the last review round (`873827f`). They
  were checked only by the closure verification for this record, including a
  regression check for each. Finding 51 is closed by this record itself.
- **Critical and high findings without a regression test.** Finding 17 (high)
  is enforced by the release workflow at run time; no automated test exercises
  it.
- **Medium findings without a regression test.** Findings 47 and 49 are fixed
  in code (`Zeroize` on drop, zeroizing seed buffers, a redacting `Debug`),
  confirmed in round 8 and read at `efb7f12`, but no test fails if they
  regress.
- **Accepted, critical-rated design gap.** Finding 38 was rated critical as a
  design requirement for a future session fast path. v2.0 has no session fast
  path, so there is no v2 code to fix; the risk accepted is that v1 session
  claims cannot be made for v2 until 2.1.

## External independent review

External independent review is **not** a gate for `2.0.0-beta.1`. Releasing
the beta without it is an explicitly accepted risk under SPEC-v2 §8.1 and is
stated in the beta release notes. An external independent cryptographic and
protocol review of the final schema, vectors and every SDK, with every P0 and
P1 finding fixed and re-reviewed, is a gate for `2.0.0` (SPEC-v2 §8.2). Until
then no v2 release carries a production security claim.

### Method

Each round reviewed five areas, each by two independent reviewers working
from the specification and the code, writing and running their own tests
in every SDK:

1. the verifier algorithm and its ordering (SPEC-v2 §6);
2. the decision lifecycle and the reference stores, including real
   concurrency, restart and lease expiry (§6.9, §7);
3. the C ABI's memory and thread safety, under AddressSanitizer,
   UndefinedBehaviorSanitizer and ThreadSanitizer (C side), with macOS
   `leaks`;
4. cross-SDK equivalence on the wire and signature layer, by differential
   testing: the largest pass fed 30,227 distinct inputs to Go, TypeScript,
   Python (native and pure), Rust and C and compared every result and error
   class;
5. the completeness and cross-SDK consistency of every earlier fix.

A release-readiness check also ran every gate and compared the published
claims with measured results.

### Outcome

- **One spec-required DENY was found returning ALLOW,** in Python only: a
  `time_window` whose zone name differed from a database zone only by letter
  case was found through a case-insensitive filesystem and could pass. Fixed
  in `90ee4c0`; every SDK now runs shared vectors for case-variant names.
- **One committed result could change its release outcome:** a `withheld`
  release could become `released` on a later call after the clock
  recovered. A withheld result is now recorded and permanent (§6.9), with
  shared vectors.
- **SDK divergences** (the same input decided differently by two SDKs) were
  found in the status evidence batch decoder, decode-versus-configuration
  order, lease-expiry recovery validation and TypeScript's handling of very
  large transaction receipts. All are fixed, and shared vectors now pin each
  rule.
- **Specification drift**, where every SDK agreed but the text said
  otherwise, was resolved: the spec now follows the safer reading or the
  code now follows the spec, case by case, with vectors.
- **C ABI**: no memory-safety defect was found in library code under the
  sanitizers. Boundary hardening was added for forged lengths and counts from
  callers and callbacks, embedded NUL and non-UTF-8 callback text, and output
  clearing.
- **Verifier configuration**: the live verifier now requires the deployment's
  verifier key ID (§2.4, §6.1), so a proof or challenge naming another
  verifier fails before the claim.
- **Final round** (against `bfd59e5` and `c1e3afd`): the ordering, lifecycle,
  wire and fix-completeness reviews found no defect. Two earlier fixes that
  had not reached every implementation (Python's terminal-error context and
  the edge sentinel reference's own store) were completed in `d901702`. A
  panic-path output leak reachable only through the test-only panic hook is
  documented as an invariant in `sdks/c/src/guard.rs`.
- **Readiness check** (against `08f0e47`): every measured count matched the
  release notes. The TypeScript and Python randomized decoder suites did not
  cover the `SecurityJournalV2` snapshot importer that §8.1 item 2 names;
  they do from `153b2ee`. Go and Rust already fuzzed it.
- **Confirmation round** (against `b6db317`): the ordering and C ABI reviews
  found no defect. Two reference-store defects were found by calling a store
  directly, which the verifier never does, and fixed in `f87afbe`: the
  reference claim stores trusted a supplied claim ID, so two claims could be
  created for one challenge, and the edge sentinel reference store kept an
  invalid evaluation progress record, which stranded that claim's recovery.
- **Round 6** (ten passes against `f87afbe` through `2be537f`; each pass
  reviewed the lifecycle, C ABI and fix-completeness areas again after the
  previous pass's fixes):
  - **One spec-required DENY was found returning ALLOW, in every SDK.**
    Release step 7 compared the finalization time with the acknowledgement
    time but did not check that the finalization time was a timestamp
    (§2.5). A claim store answering a negative `finalized_at` released a
    committed allow. Release now withholds it as `clock_regressed` (§6.9
    step 7), with a test in each SDK. Fixed in `711037a`.
  - **C store boundary.** The C stores did not check that a claim ID is
    derived from the claim's replay key. Recovery accepted a claim record

    compare the claim view's other fields with the sealed record. A NULL
    callback slice with a nonzero length was read as empty, and so was a
    NULL audience domain list with a nonzero count, which must be
    `constraint_unverifiable` (§6.11). Each is now refused. Fixed in
    `6fd56b2`, `087783f`, `e49af55`, `1d35142` and `2be537f`.
  - **Checkpoints (§7.8).** The reference checkpoints in every SDK and the
    edge sentinel accepted an acknowledgement time outside the timestamp
    domain. The plain C test checkpoint acknowledged out of order and did
    not freeze on a fork. The edge checkpoint answered an identical retry
    after a fork with an error, did not check the retry's predecessor, and
    read its clock before answering a retry. The reference clocks now refuse
    a reading outside the domain as `claim_store_unavailable`. Fixed in
    `112e8a4`, `711037a` and `1c14464`. The edge state digest is an edge
    profile field outside the §7.8 retry tuple and changes as state
    advances, so it is not part of retry identity.
  - **Plain C test store.** It committed an allow with no horizon and issued
    predictable owner tokens. It now applies the edge store's commit rules

    `711037a`.

    fix-completeness reviews found no defect. Three type errors in
    TypeScript test files, which the CI type check of the sources does not

- **Round 7** (a first pass against `6e4875d` and a second against

  the candidate. **No spec-required DENY was found returning ALLOW.**

    unchanged; it is now cleared (`afbde82`). Shared vectors for damaged and
    substituted resumption records, abandoned claims and resumption races

  - **Transaction receipt precedence (every SDK).** Decoders compared the
    received bytes with the canonical encoding last, so a non-canonical
    receipt with a second fault reported the later class instead of
    `malformed` (§2.1). Every input was still rejected. Fixed in `01d1556`.
  - **C ABI evaluator registration.** A custom registration with a NULL

    claim. Fixed in `7106037`.
  - **Sealed terminal result (every SDK).** Finalization, recovery and
    resumption compared only the decision and reason of the terminal

### Known limits of this review

- Concurrency is tested in every SDK against its reference store; shared
  vectors cannot express real concurrency, so cross-SDK race behaviour is
  pinned only by each SDK's own suite.
- ThreadSanitizer instrumented the C side only; the Rust library was not
  rebuilt with an instrumented standard library. LeakSanitizer is not
  available on the macOS hosts used; leak checks used macOS `leaks`.
- Misusing the C ABI's ownership contract (freeing a buffer twice, freeing a
  handle and then using it, or freeing with the wrong function) is undefined
  behaviour under §1.3; under AddressSanitizer each such call crashes rather
  than being reported.
- One LangChain reference test failed with an HTTP `400` in two of about
  nine full gate runs (at `f87afbe` and `2be537f`). Both failures were on
  the only request that carries the signed presentation header, about 38 KB,
  which exceeds the HTTP parser's default 16 KiB buffer for incomplete
  headers when the headers arrive in several reads. That behaviour was
  reproduced directly and fixed in `d62bed2`, with a test. A CPU-load loop
  did not reproduce the original failure, so the link to the two recorded
  failures rests on where they occurred.
- Crash injection is a process crash at every durable step (the Go
  reference stores and the edge sentinel); it keeps the page cache, so lost
  unsynced writes from power loss are not modelled. Shared vectors cannot
  express C pointer and length faults; those are pinned by the C suites
  only.
- No shared vector carries a transaction receipt at the 32 and 33 party
  limits (each party needs its own keys, about 2.2 MB of vector data); the
  SDK suites test those limits. The crafted small-order and mixed-order
  Ed25519 key vectors place the key on a certificate issuer only.
- Finding 61 stands: no external independent cryptographic and protocol
  review has taken place. It is a gate for `2.0.0`, not this beta.
