# Ratify Protocol v2.0.0-beta.1 (draft release notes)

**Draft.** Not published. Counts, commits and package versions must be
re-measured and filled in at the tag commit before release.

## Summary

Ratify Protocol v2 is a separately versioned wire profile for portable
authority proofs: cryptographic proof that an AI agent was authorized to act
on someone's behalf, checkable by the receiving side without calling back to
whoever issued it. It keeps the hybrid Ed25519 and ML-DSA-65 signatures of v1
and changes how a verifier reaches a decision: verification commits a result
and a signed receipt first, and only a released decision is actionable.

`2.0.0-beta.1` freezes the v2 wire format and SDK API in Go, TypeScript,
Python, Rust and C. It is a prerelease.

## Review status

- Review so far is **internal adversarial review** of the specification, the
  shared vectors and every SDK. The closure record, the exact package commits
  and every SDK's test results are recorded with the tag.
- **External independent review has not happened yet.** Releasing the beta
  without it is an explicitly accepted risk (SPEC-v2 §8.1).
- External review, interoperability with at least one implementation outside
  this repository, and a recorded soak are gates for `2.0.0` (SPEC-v2 §8.2).
  Until then no v2 release carries a production security claim.

## What's new

- **Verify, then release.** `VerifyProofBundleV2` commits a terminal result
  and a receipt body that are not actionable. `ReleaseV2Decision` returns the
  only actionable decision, after the signed receipt is appended to an
  ordered log, an independent checkpoint has acknowledged it, and the
  challenge and allow deadlines are still current. Applications gate each
  side effect on `Allowed(clock)`.
- **Signed status under a separate status key,** applied through an anchored
  `SecurityJournalV2`. An allow always requires current status for every
  certificate in the chain. Every SDK ships a minimal status publisher.
- **Stored challenges.** The issuance helper persists each challenge before
  it returns it; the verifier claims it atomically, so a replay is never
  evaluated.
- **Receipts for every terminal result** in a hash-chained log with
  checkpoint acknowledgements.
- **Exact `custom:` scopes:** one exact `custom:<name>` required scope, listed
  by every certificate in the chain; `custom:*` is invalid.
- **Extension evaluator profiles** registered by the verifier, with the
  standard `com.ratifyprotocol.max_count/v1` and
  `com.ratifyprotocol.allowed_values/v1`. The profile digests a decision used
  are signed into its receipt.
- **A closed constraint registry with integer-only numbers:** `time_window`
  (pinned IANA tzdata), `max_amount` in micro-units, `max_rate`,
  `resource_path`, `ratify.receiver_audience`.
- **Typed and external signers.** No SDK signs caller-chosen bytes. An
  external provider can hold the private key; the SDK verifies every
  returned signature before use. No claim is made about any particular KMS
  or HSM.
- **Wire limits** checked before parsing, a closed table of **49 error
  classes**, finite delegation lifetimes, and **deployment profiles** for a
  single offline device, dual-root approval and middleware custody.
- **Runnable examples** in all five languages under `examples/v2/`, with
  identical output checked in CI.

## v1 and v2 compared

| Area | Ratify Protocol v1 | Ratify Protocol v2 (2.0.0-beta.1) |
|---|---|---|
| Signatures | Hybrid Ed25519 and ML-DSA-65 over canonical bytes | Same algorithms over a domain-separated message that names the object type, with a fixed ML-DSA context per type |
| Key IDs | 128-bit v1 ID | Full 256-bit `key_id_v2`; trust is pinned to complete keys |
| Numbers | Floats allowed in some constraints | Integers only; amounts in micro-units |
| Decision | `Verify` returns a status | A committed outcome, actionable only after release (receipt verified, checkpoint acknowledged, deadlines current) |
| Revocation | Provider callback, which may be unsigned or boolean | Signed lists and pushes under a separate status key, applied through an anchored journal; an allow requires current status |
| Audit | Optional receipts and audit hook | A signed receipt for every terminal result, in a hash-chained log with an independent checkpoint |
| Replay | Optional challenge store | A stored challenge and an atomic claim are required for a live decision |
| Custom scopes | `custom:` accepted as a required scope | One exact `custom:` scope, listed by every certificate in the chain; `custom:*` is invalid |
| Constraints | Eight built-in types plus a local evaluator hook | Closed registry of five types plus registered evaluator profiles whose digests are signed into the receipt |
| Geo and speed | Supported | Planned for 2.1 |
| Session fast path | SessionToken | Planned for 2.1 |
| Agent-to-agent mutual presentation | Documented pattern | Planned for 2.1 |
| HTTP and registry bindings | Specified | Planned for 2.1 |
| Expiry | No-expiry sentinel allowed | Finite expiry, at most ten years |
| Limits | Depth and identifier limits | Per-object byte limits checked before parsing |
| Deployment profiles | Middleware custody | Single-device offline, dual-root composition, middleware custody |
| Errors | Status strings | A closed table of 49 error classes |
| Packages | Go module root, npm 1.x, `ratify-protocol` (PyPI), crate 1.x, `ratify-c` 1.x | Go `/v2` module, npm 2.x (dist-tag `next`), `ratify-protocol-v2` (PyPI), crate 2.x, `ratify-c` 2.x ABI |

## Compatibility

- **v2 is not backward compatible with v1.** A v2 verifier rejects v1
  objects, and there is no automatic fallback in either direction.
- **Migration is a clean re-enrollment:** fresh v2 keys, proof of
  possession, and new v2 delegations. No v1 key can authorize a v2 key.
- **Side-by-side operation is supported.** v1 and v2 packages install
  together in every ecosystem, and a deployment chooses the version at each
  boundary.
- **v1 remains available and pinned.** Released v1 tags and artifacts are not
  moved or replaced. There is no fixed, dated v1 support window today; v1
  support terms will be announced with `2.0.0`.
- **v1-only until 2.1:** the SessionToken fast path, the A2A mutual
  presentation profile, the HTTP and registry bindings, and the geo and speed
  constraints. Claims that depend on them remain v1 claims.

Upgrade guide: [`docs/PROTOCOL_V2_MIGRATION.md`](../PROTOCOL_V2_MIGRATION.md).

## Install

| SDK | Protocol v2 | Protocol v1 (unchanged) |
|---|---|---|
| Go | `go get github.com/identities-ai/ratify-protocol/v2@v2.0.0-beta.1` | `go get github.com/identities-ai/ratify-protocol@v1.0.0-alpha.20` |
| TypeScript | `npm install @identities-ai/ratify-protocol@2.0.0-beta.1` (or `@next`; import `@identities-ai/ratify-protocol/v2`) | `npm install @identities-ai/ratify-protocol@1.0.0-alpha.20` |
| Python | `pip install ratify-protocol-v2==2.0.0b1` (import `ratify_protocol_v2`) | `pip install ratify-protocol==1.0.0a20` |
| Rust | `cargo add ratify-protocol@2.0.0-beta.1` (module `ratify_protocol::v2`) | `ratify-protocol = "=1.0.0-alpha.20"` |
| C/C++ | `ratify-c` 2.0.0-beta.1 release archive (`ratify_v2_*` ABI, check `ratify_v2_abi_version()`) | `ratify-c` 1.0.0-alpha.20 release archive |

An unpinned npm install keeps resolving to v1 until `2.0.0`.

## Known limits

- The SDKs' in-memory reference stores (claim store, receipt log,
  checkpoint, journal and issuance stores) are for tests and examples only.
  Production needs durable Part B stores and an independent checkpoint in a
  separate failure domain (SPEC-v2 §7).
- Embedded v2 targets other than armv7 Linux (Raspberry Pi 2) are untested.
- The external signer interface makes no claim about any particular KMS or
  HSM.
- No reference integration is described as v2-compatible until its own gate
  passes on v2 with recorded versions; see
  [`docs/V2_REFERENCE_COMPATIBILITY.md`](../V2_REFERENCE_COMPATIBILITY.md).
- The managed Ratify Verify service does not offer v2 yet.
