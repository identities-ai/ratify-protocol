# Negative wire-acceptance corpus

`cases.json` holds byte-identical malformed documents that every SDK's
untrusted JSON entry point must refuse to accept as a valid `ProofBundle`
or `SessionToken`. Each case's document is stored base64-encoded
(`doc_b64`) so byte-level cases — malformed UTF-8, BOM prefixes — survive
being embedded in a JSON manifest.

This directory is deliberately a sibling of `testvectors/v1/`, not part of
it: `v1/` holds canonical fixtures for **valid** protocol behavior and its
file count is release-gated. Nothing here is a protocol fixture; these are
acceptance tests for the SDKs' wire boundaries.

## The contract

For every case, an SDK's untrusted entry point MUST NOT accept the
document as valid. Two outcomes satisfy that, and `strictness` says which
apply:

- **`decode`** — every SDK must reject the document before verification
  (a decode/parse error). These defects are visible to any strict parser:
  duplicate keys, unknown fields in signed structures, integers outside
  the safe-integer range [-(2^53-1), 2^53-1] (SPEC §6.2), malformed
  base64, malformed UTF-8, BOM prefixes.
- **`decode_or_verify`** — SDKs whose wire codecs validate cryptographic
  byte lengths and chain depth at decode time (TypeScript, Python) reject
  these at decode; SDKs that parse structurally and validate during
  verification (Go, Rust, C) may parse them, but the public verify entry
  point must then return an invalid result. Either way the document is
  never accepted.

What is NOT acceptable, for any case, in any SDK: a decode that succeeds
followed by a verification that reports the bundle valid.

## Case targets

- `target: "bundle"` — drive through the ProofBundle decode/verify path.
- `target: "token"` — drive through the SessionToken decode path.

## Consumers

- TypeScript: `sdks/typescript/test/wire.test.ts`
- Python: `sdks/python/tests/test_wire.py`
- Go: `wire_check_test.go` (module root)
- Rust: `sdks/rust/tests/wire_negative.rs`
- C: `sdks/c/tests/api.rs` (drives the public `ratify_verify_bundle` and
  session-token JSON functions)

The corpus is regenerated by hand when a new rejection class is added;
documents derive from `testvectors/v1/happy_path_depth_1.json` and
`session_token_valid.json` with a single defect spliced in, so rejection
is attributable to that defect alone.
